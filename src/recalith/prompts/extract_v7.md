Extract durable project knowledge from the request's events and episodes: facts, decisions, preferences, failure lessons and procedures that a later session of this project would need. Prefer no claim over a weak one; an empty proposal with a no_op_reason is a correct answer when nothing durable happened. A user's explicit statement for this project, such as "Decision for this project: ...", "Remember ..." or "Keep ... for my planning", is durable in itself, even when the session's tools only read files or none ran. Propose a stated rule, decision or preference as a user_declared decision or preference citing those words. Propose a statement of how the project is, such as where it stores its data or which file, format or command it uses, as a user_declared fact citing those words, with the file dependencies described below, so a later change to that file is labeled instead of delivered as current.

Return propose_claim operations (and attach_evidence or revise_claim for an existing claim in claims, naming its exact claim_ref). Every claim cites its evidence with exact record ids and revisions from allowed_evidence_refs; a quote uses a locator with exact code-point offsets into the stored field and the SHA-256 of the quoted text. Each operation's evidence is its own evidence array, beside payload, never a key inside payload: a payload holds only the keys output_schema gives its kind, so a propose_claim payload has no evidence, claim_ref or supersedes, and an existing claim changes only through attach_evidence or revise_claim naming its claim_ref. Say no more than the cited evidence shows: add no requirement, type, unit, time zone, default, consequence or limit it does not state (such as "to a directory", "in UTC", or only, always, every and never), and never present a parameter's default as what always happens. Word a user's declaration or correction from the user's own words: a claim replacing an existing one states the new value as the user stated it, not in the replaced claim's framing.

Choose the basis honestly; code checks it mechanically and refuses anything else:
- observed: only a fact that restates one typed tool result exactly. Each support link names a mapping. tool.exit_code (a finished call with a numeric exit_code; locator null) makes the proposition exactly "`<argv joined by single spaces, or the tool name when the call has no exact argv>` exited with code <exit_code>." tool.reported_result (locator on the whole assertions.<n>.value string of a test_result or parsed_value assertion) makes it exactly "`<the same invocation label>` reported <kind> <identity>: <value> (passed)." or "(failed)." per the assertion's passed field, or with no parenthesis when passed is null. Any cause, explanation, lesson or wider statement is not observed.
- user_declared: only an actual statement of intent or preference by the user, cited by a locator on the user's own words. Text inside code fences, blockquotes, attachments, pasted emails, diffs, logs, tracebacks or terminal output is never a declaration, even when it says "I want".
- inferred: everything else, including every cause, lesson and generalization. Inferred claims are reviewed adversarially before they are used.

A failure_lesson must cite a tool result whose recorded outcome is failure; code refuses one that cites none. When a call finished with exit code 0 but its output shows a failure, because a pipe such as `| tail` or a later command in the same call hid the failing command's exit status, that failure is not recorded as one: state what the output shows as an inferred fact citing that output, never as a failure_lesson. Word that fact as the project's condition that a later session can act on, such as "Running `<command>` from <where>, without <setting>, fails with <quoted error>.", not as an account of one call, its recorded exit status or the pipe. Claim no more than the runs showed: one failing form and one passing form do not show that the passing form is the only one that works.

Declare the files a claim describes. When a fact, procedure or failure lesson states what a workspace file contains or how the code in it behaves, whether a tool result showed it or the user stated it, list in dependencies each file the events show it describes, such as the module a read showed implementing the stated behavior, as {"kind": "file", "key": "<path>", "fingerprint": null, "record": null}, where <path> is the workspace-relative path exactly as an event's payload.action.paths gives it. Code records the file's current content, so a later change labels the claim for revalidation instead of delivering it as current. Never guess a path or give an absolute one, and declare no config or environment dependency. A decision or preference states intent: it has no file dependency unless its own words make it conditional on one.

Use the narrowest scope the evidence justifies: never name a workspace or path the evidence does not concern, and add conditions only from the condition schema. For a failure_lesson leave failure.last_supporting_failure_event_id and failure.action_family_digest null (code derives them from the cited failure) and state retry_conditions when a retry could legitimately succeed; a failed exit status alone does not justify a general lesson. For each pending entry in boundaries you may return resolve_task_binding with that boundary's binding_revisions as expected_binding_revisions, or leave it pending. Never put confidence, rationale or instructions for the reviewer anywhere but reason.
