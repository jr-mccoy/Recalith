# Round-three review response and final handoff

Revision 1.3 • 2026-10-15 • Supersedes v1.2 for implementation.

The third review's main conclusion stands: **start building after the early compatibility probes**. This final downloadable snapshot incorporates the requested corrections into the full specification. It is not a request for another design-review cycle. Once the new repository exists, its version-controlled documents and tests become the design authority, with Tasks 0 and 0b establishing the first empirical facts before Task 1.

This response addresses all **seven main findings and fourteen smaller fixes** in the supplied [round-three review](../review/ROUND_3_REVIEW.md). The IDs below track review dispositions; the acceptance suite remains **73 cases**, with **67 preview case IDs** and their explicit variants. Adding Task 0b brings the plan to **22 work packages**. This response explains changes; the integrated specification and contracts define behavior.

## What changed

- **Memory survives age-based retention.** Primary evidence and necessary support paths remain pinned while live claims or open work depend on them. Unreferenced payloads expire at 180 days in preview; forgetting overrides pins. Full-release capsules save space and support transfer, with retained originals when preservation is insufficient.
- **Launch and operator workflows are defined.** Workers and curators get explicit child environments and distinct role markers. An operator can create a token before initialization for an unmarked noninteractive harness. The strict marker refusal remains, with a documented ordinary external-terminal route for IDE users.
- **Delivery feasibility moves to the beginning.** Task 0b tests the four delivery paths without an engine. Later integration tests must repeat the protocol through the real product.
- **Explicit decisions get review priority.** Declaration and high-impact correction review outrank ordinary review when the next eligible model slot and budget are available. Budget exhaustion remains visible; a priority label cannot create more capacity or skip review.
- **Full release upgrades the existing installation.** A verified maintenance migration preserves memory, IDs, privacy tombstones, and explicit configuration. Capability probes, pin/capsule handling, chain baselining, and recoverable activation are defined.

## Qualifications that matter during implementation

1. **Pins preserve support, not freshness.** Day 181 alone no longer removes evidence. Independent freshness, dependency-change, contradiction, quarantine, or privacy rules can still reduce guidance. Pinning bounds neither total live-claim count nor storage by a fixed number; surface pinned bytes and use explicit capacity/backpressure policy rather than silently evicting live support.
2. **Preserve the complete support path.** Pinning only a root ID while deleting its excerpt or necessary intermediate locator would leave a dangling claim. Reachability includes required content and must be checked in the same serialized transaction as admission/expiry. Generated summaries do not replace primary support merely because they are smaller.
3. **Tokens provision automation; they do not prove humanity.** A pre-init token must already come from an unmarked operator workflow. Its verifier applies to the installation created with it. Revoking it locally does not revoke the standalone bootstrap file everywhere; remove that file or its CI secret separately to prevent future reuse. Same-user processes remain outside this guard's security guarantees.
4. **Stripping markers is necessary but insufficient isolation.** Effective tools, hooks, native memory, MCP, managed policy, config, and selected auth still require the existing probe. Fresh worker and curator markers have different meanings so ordinary worker ingestion is not mistaken for recursive curator output.
5. **Full activation does not require perfect compaction.** If an exact sufficient capsule cannot preserve a pinned payload, retain the original with its pin and report deferred compaction. Do not block memory survival, fabricate new independent support, or downgrade a supported claim merely to meet a shorter default retention period.
6. **Probe evidence is still missing.** This revision defines what to measure; it does not certify host isolation, Windows detachment, delivery usefulness, latency, or budget fit. Those facts belong to Tasks 0/0b and subsequent implementation gates. No new product repo, implementation, or benchmark run is included here.

## Preserved decisions

Each project continues to own its complete engine, worker, configuration, store, and memory. Short-term state, medium-term episodes, and long-term claims are separate functional representations joined by evidence lineage, not a timer that blindly promotes text. Capture, review, recall, revision, and maintenance remain autonomous within configured budgets and host capabilities. A personal external brain is another independent project.

Use a fresh repository. Breadcrumbs remains an optional pinned reference and later one-way import source; do not clone its implementation as the new product. The preview/full split, no declaration-review bypass, evidence-strength model, protected review budget, forgetting guarantees, and comparative evaluation requirements are retained.

The complete specification is preserved in the modular package and combined download. Historical reviews and prior responses remain unchanged and are clearly marked as superseded inputs.
