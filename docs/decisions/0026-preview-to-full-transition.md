# Decision 0026: The preview-to-full profile transition

Status: accepted (Task 17 full, the transition slice; Cut 2) · Date: 2026-10-23 · Observed: deterministic tests on real preview stores (real captured events, claims admitted through the real extraction/review path, a real forget), real operator children killed with `os._exit`, the installation's real worker process recovering them; no live route needed (B1 still open)

## Context

SYSTEM_SPEC §10.1 defines the guarded `recalith upgrade --wheel PATH --expected-digest DIGEST --release-profile full`: an existing preview installation moves to the full profile in place, under exclusive maintenance, after a verified backup with the current tombstone ledger, through a staged store and an activation/rollback journal; IDs are preserved, the revision chain gets an activation baseline, profile-default retention moves from 180 to 30 days while explicit operator overrides stay, pinned payloads become exact capsules or keep their pins, capabilities are re-registered and probed, activation is one recoverable state, and a full-to-preview request is `policy_refused`. DATA_CONTRACTS §11 defines `UpgradeResult`. Task 5's full slice (decision 0024: the chain and `establish_baseline(txn, reason="activation")`) and Task 15's capsule slice (decision 0025) are built but could act in no real installation because no full store could exist.

The documents left open: the slice boundary between this transition and a general engine upgrade; whether a successful transition makes the full profile available to real installations now; where operator retention overrides live and which profile governs an installation's defaults; the journal, its recovery points and the rollback rules; how capsule conversion and deferred compaction are reported; what happens to a `migration_required` store. This record settles them. Nothing here relaxes a preview rule.

## Decisions

1. **Slice boundary.** Built: the in-place **profile transition** `operations.upgrade.transition(ctx, wheel, *, expected_digest, release_profile, now=None, inherited=None, stop_wait=None) -> UpgradeResult`, run by the engine the installation already pins, its recovery `operations.upgrade.recover(ctx, *, held=False)`, the worker's call to it at start, health reporting and the service/CLI wiring. Not built (Task 17 full remainder): the side-by-side engine switch between two releases (a second runtime under `.recalith/runtime/`, switching `engine.lock` and the launchers at activation, the bootstrap's own upgrade entry point), same-profile engine upgrades, schema migration of older stores, per-project OS startup entries. `side_by_side_upgrade` stays unavailable in both profiles.

2. **The supplied wheel.** The transition verifies the artifact before anything else changes: the file name is a recalith pure-Python wheel, its SHA-256 equals `--expected-digest` (else `invalid_schema`, exit 2), its version equals the running engine's and the installation's `engine.lock` pin (else `capability_unavailable`: switching engines is not built), and for a wheel-provisioned pin (`provisioning = "wheel"`) the pin's `artifact_sha256` and the provisioned runtime's record equal the wheel's digest. A source-tree pin (development checkouts, the test fixtures) has no artifact digest to compare; the wheel's own digest is verified and recorded (`artifact_sha256` in the autonomy log). The wheel is never installed by the transition: provisioning stays the release bootstrap's job.

3. **Availability (owner question).** `FULL_RELEASE_AVAILABLE = False` in `operations/upgrade.py` is the one build constant for both gates: `service.upgrade` and the guarded CLI answer `capability_unavailable` (exit 4) after the operator guard for every form except a full-to-preview request on a full store (`policy_refused`, exit 6), and `init --release-profile full` stays refused (decision 0024). The transition is reached only through the operations function, which the test suite exercises; there is no environment variable, flag or configuration that enables it. Reasons to keep it off until the owner decides: the rest of the full release (Codex/generic JSON/MCP, transfers, session mode, IPC wake, the engine switch, installed private-path rules) is not built, and without IPC wake the full profile's 30-second idle poll would miss the preview's typed-state target (§7). Flipping the constant is the owner's decision; nothing else in this slice depends on it.

4. **Profile authority and retention overrides.** The installation's profile is the one its **store** records (`installation_meta.release_profile`). `identity.installation_config(root)` builds the effective `ProjectConfig` from that profile's defaults and `project.toml`; the retention configuration, the worker's configuration and health all use it. The tracked `release_profile` in `project.toml` is a record (it is the fallback only when no store can be read): editing it activates nothing, and a clone whose tracked file says `full` keeps its own preview store's defaults. Explicit operator retention overrides live in `project.toml` as a `[retention]` table of positive whole days keyed by the `RetentionConfig` fields (`unpinned_event_payload = 120`); each becomes `{days, source: operator_override}`, every other value is `{days, source: profile_default}` for the store's profile; anything else in the table is `invalid_schema`. So the 180→30-day change of the transition is exactly the store's profile changing; overrides are untouched, and an override equal to a default stays an override.

5. **Procedure** (one operator command; the actor must be the operator).
   1. Refusals before any effect: a downgrade (`policy_refused`); a same-profile request (`capability_unavailable`); a store at another schema (`capability_unavailable`, item 9); the wheel checks of item 2.
   2. Exclusive maintenance: the privacy-maintenance lock (no forget, restore or second transition runs alongside), the worker stopped and its installation lock held for the whole operation (the next hook restarts it), a journaled restore refused, an unfinished forget finished first, the maintenance marker written (kind `upgrade`: the hook pauses delivery, the model lane leases nothing), the journal `.recalith/run/upgrade.json` (0600, atomic, fsynced).
   3. A verified backup with the current tombstone ledger (`.recalith/backups/upgrade-…`, the ordinary backup path). If it fails nothing is staged: `not_activated` with `backup_failed`, no backup ID.
   4. Capability registration (item 7).
   5. Staging, in memory, from a consistent snapshot of the live store (SQLite's backup interface from a read-only connection), with a content digest of every chained table's rows: first the capsule step under the **target** retention window (decision 0025's sufficiency rules and `retention._compact`, one transaction, all candidates); then the **activation transaction**: profile `full`, policy revision and guidance epoch advanced (a read set or a serving fence from before no longer matches), the content-free `profile_transition` operation (the autonomy log entry) and, last, `integrity.establish_baseline(txn, reason="activation")` over every current row. Every live claim's support links that were available must still be available; the staged chain must verify over every row with `pre_baseline_history: not_chained`. The staged file is written beside the live store (`.recalith/state/upgrade-….sqlite`, via a `.partial` file).
   6. Activation: the journal records `activating` — **the commit point** — then the live store must still hold exactly the snapshot's rows (the content digest; a write since the snapshot, such as an operator command or a forget, aborts to `rolled_back` with `store_changed_during_upgrade`) and the staged file its recorded digest; the live store is quiesced (WAL folded, sidecars removed) and the staged file replaces it with one atomic rename. Then the journal says `activated` and the completion runs: the verifier checkpoint of the staged full check (only if the live chain has exactly that head), the tracked `release_profile` record in `project.toml` (only that line changes; every other byte is kept), the latest ledger copy, the journal removed, the marker released, the result recorded in the private `.recalith/state/upgrade.json`.

6. **Recovery points and rollback.** The journal phases are `fenced`, `backed_up`, `registered`, `staging`, `staged`, `activating`, `activated`. Before `activating` the live store was never touched: a failure in the operation, or recovery after a crash, removes the staged files and the journal, releases the marker and reports `rolled_back` (with a verified backup; `not_activated` without one); the operator re-runs the command. From `activating` on, recovery activates: if the staged file is still there it is swapped in under the same content-digest fence (a changed live store rolls back instead), and completion runs; after the swap the live store is the complete full store, so completion only finishes the record, checkpoint, ledger copy and marker. A failure in completion returns `recovery_required` with the journal kept; the worker's next start completes it. A journal whose activation cannot be confirmed (no staged file and no matching store) stays `recovery_required` with `activation_state_unknown`. No half-migrated store ever serves: the live path holds either the complete preview store or the complete full store, and the rename is the only switch. Recovery runs in the worker's start (holding its installation lock) before the store is opened and when a transition finds an interrupted one; it needs the privacy lock and never runs beside a transition.

7. **Capability registration.** Before staging, the registry is computed and stored in the autonomy log entry: `eligible` (the full features this engine builds: `revision_chain`, `capsules`), `not_activated` (`codex_capture`, `codex_delivery`, `generic_json`, `mcp`: eligible for explicit configuration only, never activated by the transition), `unavailable` (every other deferred feature, `not_built_in_this_engine`), the provider route probed again with `route_status(…, observe=True)` (the executable's version observation is the only launch; no model call, outside every transaction), and each delivery path `certified` exactly when health reports it healthy from the installation's own live certification record, ignoring only the transition's own maintenance marker. The transition certifies nothing and changes no provider, route or delivery path: health after activation reports every required and optional capability from the same evidence as before, plus `revision_chain` and `capsules` from the full store.

8. **Reporting capsules and retained pins.** `UpgradeResult` keeps its contract: `retained_pin_count` is the number of pinned payloads past the target window still held in full after the capsule step (the same measure as `RetentionSummary.deferred_compaction_count`); `baseline_digest` is the baseline entry's hash; both are reported only for `activated` and `recovery_required`. The autonomy log entry adds the per-reason deferral counts, the compacted count, the redirected links, the cutoff, the retention before/after per value with its source, the registry, the backup ID, the artifact digest and the new policy revision and guidance epoch; it is content-free (counts, codes, IDs, digests) and `forget` keeps it as such. The capsule step writes its own content-free `retention_capsule` operation. Unpinned payloads are not expired by the transition: the worker's next sweep applies the new window (ordinary retention).

9. **`migration_required` stores.** No schema change is needed: `SCHEMA_VERSION` stays 11; preview stores and backups stay writable and restorable. A store at another schema is refused before any effect (`capability_unavailable`, byte-identical): migrating it is the general engine/schema upgrade, not built. The transition does not become a path out of `migration_required`.

10. **Health.** In both profiles `recovery.coverage.upgrade = {journal: <phase>|null, last: {operation_id, state, source_profile, target_profile, retained_pin_count, error_codes}|null}`; a journaled transition adds `upgrade_recovery_pending` (degraded) and keeps the maintenance marker `active` (delivery paused) until recovery. `release_profile` comes from the store. Preview health is otherwise unchanged; after activation the full report is decision 0024's and 0025's.

11. **Interplay with forgetting and restore.** A transition and a forget or restore never run together (one privacy-maintenance lock). After a crash, forgetting stays possible (privacy first): its marker release keeps the marker while a transition is journaled; a forget on the preview store before the swap makes the swap's content-digest fence roll the transition back; one after the swap applies to the full store. A restore is refused while a transition is journaled, and a transition while a restore is. The transition's backup holds the tombstones current at its start; the staged store is a copy of the live store, so every tombstone and target is carried over and nothing forgotten is resurrected.

12. **Failure injection.** New family `failpoints.UPGRADE`: `upgrade.after_backup`, `upgrade.after_registration`, `upgrade.after_baseline` and `upgrade.after_capsules` (inside the staged transactions, commit pending), `upgrade.after_stage`, `upgrade.before_swap` (journal `activating`), `upgrade.after_swap`, `upgrade.after_record`. Armed only by a test in its own process. The kill/restart family `test_profile_transition_crash_matches_reference` (the UPGRADE family, the backup family's four points and the chain's two) kills only where transition or post-transition work is owed, judged from effects.

## Limits (stated, not hidden)

- **Not available to real installations** in this build (item 3); the side-by-side engine switch, same-profile upgrades and schema migration are not built.
- **Fence window.** The content-digest check and the rename are separate steps: an operator write in that instant on POSIX could be lost with the replaced file (the worker is stopped, hooks never write SQLite). Restore has the same property. On Windows the rename fails while another process holds the file open, and the operation rolls back.
- **Cost.** The snapshot is held in memory (O(store), like restore), the content digest and the staged full check are O(store).
- **Pre-baseline history** (including the transition's own capsule step) is reported `not_chained`; the chain proves nothing about it.
- **Delivery certification** of a preview installation stays valid through the transition because the engine and the hook path do not change; an engine switch (not built) would need re-certification.
