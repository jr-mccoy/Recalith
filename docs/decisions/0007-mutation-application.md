# Decision 0007: Mutation application, re-evaluation and compensating undo

Status: accepted (Task 5 preview slice) · Date: 2026-10-16

## Context

Task 5 builds `evaluate_operation` and `apply_proposal` (DATA_CONTRACTS §11) under SYSTEM_SPEC §6.2 and §10. The documents fix the rules (persist before applying, one transaction for groups + operation IDs + store revision + job completion, deterministic operation IDs, revision conflicts become bounded re-evaluation, malformed operations fail only their group, compensating undo) but leave open where the read set of a persisted proposal lives, how a malformed operation reaches application at all when the response DTO is strict, what a duplicate application returns, how far re-evaluation goes, and what an undo preview contains. Task 5 needed one answer for each. Where a rule was ambiguous the stricter reading was taken; semantic evidence rules remain Task 9.

## Decisions

1. **Schema 2.** Migration `0002.sql` adds `proposals.proposal_digest` and `proposals.read_set`, `operations.local_ref` and `operations.proposal_digest` (with job/kind indexes), and `claim_heads.content_key`. `SCHEMA_VERSION` becomes 2. No store was ever released; a schema-1 development store reports `invalid_schema` ("requires an explicit migration") and is never migrated silently (SYSTEM_SPEC §6.1); the upgrade path is Task 17.
2. **The persisted proposal carries its read set.** `apply_proposal(ctx, job, response)` has no read-set parameter, so `persist_proposal` stores the `ReadSet` the request was prepared under beside the response, inside the job's lease fence, before anything applies. `apply_proposal` refuses (`policy_refused`) a response that is not the job's persisted proposal.
3. **Proposal digest and IDs.** The proposal digest covers the operations, the no-op reason and the adapter-recorded malformed entries; usage and provenance are excluded, so two identical model outputs for one job are one proposal. Operation IDs are `op_` + SHA-256 of `[job ID, proposal digest, local ref]`. The application itself is recorded as one `operations` row (kind `apply_proposal`, or `apply_service` for a service writer) under the reserved ref `@apply`, which is not a valid local ref; it holds the `ApplyResult`. A duplicate application returns that stored result before the lease is checked (IMPLEMENTATION_PLAN "Representative executable assertions"); new application still requires the current lease generation.
4. **Malformed operations.** The worker parses a body in two levels (`parse_model_body_partitioned`): the byte cap and enclosing object are strict (`response_invalid`, retried), each operation is validated strictly on its own. An invalid operation, or one whose kind the purpose does not permit, becomes a `MalformedOperation {index, local_ref, depends_on, reason_code}` in a new adapter-owned `ModelResponse.malformed` field; its raw text is not retained. It fails exactly its dependency group. The strict `parse_model_body` remains for the model-facing schema.
5. **Groups.** Atomic groups are the connected components of the `depends_on` graph (malformed, duplicate-ref, unknown-dependency and cyclic members fail their component), applied in topological order with ties by proposal order, each inside its own SQLite savepoint in the single application transaction. A later rejection rolls back the whole group, including records an earlier member already wrote. A payload-level local ref (`replacement_local_ref`) must also be listed in `depends_on`.
6. **Conflicts apply nothing.** A changed consulted record, policy revision, tombstone epoch or `file:` fingerprint, or any operation target that is not the current head, means no operation of the proposal applies. (Records changed by earlier operations of the same application are checked against their pre-application revision.) For a job, one re-evaluation job of the same kind is queued through `jobs.enqueue` (coalescing, its idempotency key derived from the original key and the current conflict signature, input refs advanced to current heads, review priority inherited), the original job becomes `cancelled` with `reevaluation_requeued`, and a `requeue` operation row records the chain depth. After `REEVALUATION_LIMIT = 3` re-evaluations along one chain the job fails visibly with `reevaluation_limit`. A service writer receives `revision_conflict`. A read set this build cannot verify (an unregistered fingerprint kind, more than 64 fingerprints, another workspace) is rejected, not requeued, so it cannot loop.
7. **Structural admission only.** `evaluate_operation` checks the actor's permitted kinds (`core/policy.py`: the worker applies proposal kinds; the operator transport applies typed service kinds; hooks, MCP and adapters apply nothing), target/payload agreement, current revisions, the existence and availability of cited evidence in this installation (a foreign or invented ID does not exist here), evidence-root identity (a link may name only the event's own roots; delivery telemetry has none), quoted-span digests over the stored field, registered workspaces and existing tasks in scope, the claim status transition table, evidence for dispute/invalidation, and that an `observed` claim carries a mapping. It does not validate mappings, count independent roots, assign strength or review declarations (Task 9). Consequently a proposed claim is applied as a weak `candidate` (`candidate_only`); `revise_claim` produces an unreviewed candidate revision because altered content needs a fresh review; `assess_claim` changes nothing yet (`review_admission_unavailable`); `resolve_task_binding` is rejected until Task 6 (`task_binding_unavailable`).
8. **Exact duplicates.** A proposed claim whose content key (kind, proposition, proposition key, scope, conditions) matches a servable head reuses that head; it adds a revision only for support or contradiction links with new evidence-root identity, otherwise it is `duplicate_existing` with no effect. `attach_evidence` with no new root identity is `duplicate_evidence`. Repetition never refreshes support.
9. **Epochs.** Every memory-record mutation is serving-relevant and advances `guidance_epoch` once per transaction; proposal persistence, leases, job completion, requeue rows, rejected-only applications and application records are bookkeeping and advance only `store_revision`.
10. **Undo.** `preview_undo(ctx, operation_id)` (read-only, any actor) diffs the undone operation's immutable before/after revisions on top-level fields, ignoring bookkeeping and code-derived keys. A field whose current value still equals the undone value is restored; a field a later revision changed is reported as an `UndoConflict` and left alone; a record the operation created is retired (claims and episodes `archived`) when its status has not changed since; relations it added are removed. The `UndoPreview` (state `clean|partial|conflicted|nothing_to_undo`) has a digest over the compensation, the conflicts and the current head revisions. `apply_undo(ctx, operation_id, preview_digest=…)` requires an operator actor and the digest of a freshly recomputed preview, appends new revisions in one transaction (an `undo` operation row, itself undoable), and refuses when nothing can be compensated. It never restores a database snapshot or removes intervening history. The guarded `recalith undo` transport is Task 12a.
11. **Failpoints.** `proposal.before_commit`, `apply.after_group` and `service.before_commit` join the programmatic failpoints; the first two belong to `failpoints.WORKER`, the third to a new `failpoints.SERVICE` family. Nothing arms them outside a test process.
12. **Revision chain.** `revision_chain` stays reserved and empty; `storage/integrity.py` is not built and chain/full-row verification is reported unavailable (full-release A65).

## Consequences

The model lane no longer accepts a pluggable applier: `ModelRuntime` has a backend and a preparer, and every persisted proposal goes through `apply_proposal`. Task 6 replaces the `task_binding_unavailable` rejection with binding application through this path and creates tasks; Task 9 adds mapping validation, root classes, strength, review admission and the semantic supersession/invalidation gates on top of the structural checks; Task 10 adds `context` counter-observations to claim DTOs (they are stored only as normalized links today); Task 12a supplies the guarded operator transports for `correct`, `declare` and `undo`; Task 15/16 make every new body column participate in retention and forgetting; Task 17 owns the schema-1→2 development-store migration if one is ever needed.
