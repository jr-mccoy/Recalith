# Decision 0011: Claim extraction, deterministic admission, adversarial review and failure debounce

Status: accepted (Task 9) · Date: 2026-10-18 · Host observed: Claude Code 2.1.301 fixtures (capture); no live route (B1)

## Context

Task 9 builds extraction, semantic admission, review and the failure-trigger debounce (SYSTEM_SPEC §3.4–§3.5, §6.2–§6.3, §7.1–§7.2; DATA_CONTRACTS §1.1, §2.1, §5, §6, §6.2, §7.1, §8, §10, §11) on the Task 5 application path, the Task 7 request preparers and the Task 8 lineage. The documents fix the rules: observed only through a valid registered mapping; `user_declared` only from direct user evidence outside nondeclaration regions, checked by span intersection, with no first-person-verb heuristic and no declaration-review bypass; strength `weak|supported|corroborated` from independent root classes, never from retrieval or self-confidence; candidates until a supported review; persisted `ReviewBatch` snapshots in stable partitions of at most eight candidates, 96 KiB input and a 9,000-byte body; missing/duplicate/foreign/stale verdicts never activating; `revise` as objections only; `review_capacity` as a capacity failure that cannot loop; the six-event/ten-minute debounce. They leave open what makes a mapping valid against a particular proposition, which text regions are nondeclarations, where review jobs come from and how batches are partitioned and staleness is judged per candidate, what each verdict does to its candidate, where per-candidate outcomes live, how the plan's `.md` prompts fit decision 0009's versioned prompt code, when extraction runs, and how the debounce stays deterministic when the worker processes events late. Task 9 needed one answer for each. Nothing here weakens a rule; where a rule was ambiguous the stricter reading was taken.

## Decisions

1. **An observed claim is the code rendering of its mapped observation.** Admission cannot prove natural-language entailment, so "observed" is made mechanical: an `observed` claim must be kind `fact`, every support link must carry a mapping, every mapping must validate, and the proposition must equal exactly the code rendering of what those mappings observed (`admission.render_mapping`): `` `<argv joined by spaces, or the tool name>` exited with code <n>.`` for `tool.exit_code`, and `` `<label>` reported <kind> <identity>: <value> (passed|failed).`` (no parenthesis when `passed` is null) for `tool.reported_result`. A cause, lesson or any wider wording citing the same event is refused (`observed_proposition_unmapped`, `observed_requires_fact`, `observed_requires_mapping`) and can be proposed only as `inferred` (A15). A valid observed fact is admitted `apply`: active without a model, strength from lineage. The extraction prompt states the rendering exactly.
2. **Registered mapping contracts** (`admission.MAPPINGS`, validated wherever a mapping appears, whatever the basis). Both tool mappings need a certified finished result: `tool_finished` on the tool channel with `observed_tool` authority, not derived, `result_received` true (`mapping_requires_tool_result`). `tool.exit_code` needs an integer (not boolean) `exit_code` (`mapping_requires_exit_code`; a 2.1.301 success never has one, decision 0005) and a null locator or a locator on exactly the `exit_status` assertion's value (`mapping_locator_mismatch`). `tool.reported_result` needs a locator covering the whole `assertions.<n>.value` string of a `test_result` or `parsed_value` assertion (`mapping_requires_assertion`); assertions are recomputed by certified parsers at normalization, so a stored one is certified. `config.exact_value` has no registered config parser in this build and is refused (`mapping_parser_unregistered`); an unknown name is `mapping_unregistered`.
3. **Declarations.** A `user_declared` claim needs at least one direct declaration span, and *every* user-channel support span must be one (`admission.declaration_refusal`): an event that lineage classifies as a user-declaration root (an authenticated `user_message`; operator declaration/correction events come only from the Task 12a transport), its declaration field (`text`, or `statement` for operator kinds), complete coverage (not truncated, no missing context, not one part of a partitioned message: a fence may open in a part not shown), a non-blank span, and no intersection with a nondeclaration region (`declaration_requires_user_evidence`, `declaration_field_invalid`, `declaration_coverage_incomplete`, `declaration_span_empty`, `declaration_in_nondeclaration_region`). A null locator means the whole text. Record links never count as declaration evidence; tool results may add support classes (corroboration) but no authority. The host `<task-notification>` prompt (a `generic_observation`), assistant text and tool output are never declarations.
4. **Nondeclaration regions** (`core/regions.py`, pure, code points, CR/LF/CRLF alike): fenced code (an unclosed fence runs to the end); blockquotes with Markdown lazy continuation; attached/imported documents (`<document|attachment|file|pasted text|email|quote|context|source|transcript …>` to its closing tag or the end) and `[Pasted text #n …]` markers; email blocks (two adjacent header lines, an original/forwarded divider, or an "On … wrote:" line, each to the end of the text); diff blocks (`diff --git`, a `---`/`+++` pair or a hunk header, through the following diff lines); and uncertain pasted output (tracebacks through their exception line, runs of two or more log lines, terminal transcripts from a prompt line to the next blank line, Markdown indented code). Every rule errs toward a larger region; there is no first-person heuristic in either direction.
5. **Failure lessons and scope.** A `failure_lesson` must cite a certified failure (`failure_lesson_requires_failure`); code derives `last_supporting_failure_event_id` (the latest cited failure by commit order) and `action_family_digest` (`capture.normalize.action_family_digest` of that event) and refuses a model value that differs (`failure_body_mismatch`). A claim's scope may not name a workspace its event evidence does not come from (`scope_broader_than_evidence`); a procedure's successful episodes must exist (`episode_missing`); an inferred claim needs a support link (`inferred_requires_support`).
6. **Activation and strength.** A candidate becomes active only when `admission.activation_refusal` finds nothing: its links still resolve and keep their roots, its mappings and basis gates hold, its support resolves to at least one eligible root class (`no_primary_support`: assistant text, telemetry or an echo alone supports nothing), and no supporting source identity is in unresolved conflict (`source_conflict_unresolved`). `admission.assign_strength` reads lineage only: candidates (and every status but active/disputed) are weak; active guidance is supported with one class, corroborated with at least two classes, nothing blocking corroboration and no contradiction. One user's declarations collapse into one authority class, so they alone never exceed supported. Strength is recomputed whenever support or contradiction links change.
7. **Review scheduling.** Every application that writes a new or changed candidate through `propose_claim`, `attach_evidence` or `revise_claim` schedules its review in the same transaction (`review.schedule`); an assessment never does, so no verdict can loop. Each claim is reviewed at the head this application leaves (a supersession in the same application can write a newer candidate revision of its replacement). Candidates are partitioned in stable proposal order by count (at most eight, and at most `(9,000 − 2,000) // 768` by the review body), and by the exact serialized request (96 KiB); a candidate too large on its own is deferred, never truncated (`review_outcomes`: `deferred`, `review_input_oversized`). `review_requests` records each review job's origin job (or service submission), origin class (`extracted`, `typed_declaration`, `operator_declaration`, `operator_correction`) and partition. Priority stays code-assigned (`jobs.review_priority_for`): a typed declaration, or an extracted decision/preference whose declaration span passed item 3, makes its batch `correction_or_declaration`; priority orders launches and never admits.
8. **Batches and the review request** (`review.prepare`). The batch holds the job's candidates still at their scheduled revision (a newer revision has its own review; none left cancels the job, `review_candidates_stale`). The reviewer sees an allowlisted candidate view without earlier assessments or provider provenance (a proposal's `reason`, an extractor's rationale or self-confidence are not claim fields and never reach it) and exactly its batch evidence: event text is never trimmed, and a batch over the input cap fails (`review_input_oversized`, final) rather than shrink. The request's read set names no candidate revision, so one changed candidate cannot requeue the batch; each assessment is checked on its own.
9. **Assessment admission** (`review.check_assessment`). An assessment counts only for the job's own persisted batch and a candidate in it (`assessment_foreign`), exactly once per response (`assessment_duplicate`: all of a candidate's verdicts are refused), while the candidate's current revision is the batch revision with the snapshot digest and still a candidate (`candidate_stale`), citing only that candidate's own batch evidence IDs (`evidence_id_unknown`). `supported` must cite a support link (`supported_requires_support_evidence`) and pass item 6; it activates the candidate (strength from lineage) and records its `ReviewAssessment` with resolved evidence links (locators). `revise` needs an objection (`revise_requires_objection`) and only records it: the candidate and its proposition are unchanged; a strict payload means a "rewritten proposition" is a malformed operation. A substantive `reject` archives the candidate (not admitted; no falsity asserted). `reject` with the sole objection `review_capacity` records a capacity failure and leaves the candidate a weak candidate; `review_capacity` anywhere else is refused (`capacity_requires_sole_reject`). Without a persisted batch an assessment is `assessment_outside_review`. Operators cannot apply `assess_claim` at all.
10. **Per-candidate outcomes** (`review_outcomes`, content-free): `admitted`, `revise`, `rejected`, `capacity`, `duplicate`, `foreign`, `stale`, `refused` (any other admission code), `missing` (`verdict_missing`, a batch candidate no valid-shaped assessment named) and `deferred`, each with its exact reason code. A malformed assessment is not attributable (its raw text is not retained) and counts toward nothing.
11. **`review_candidates(ctx, claim_ids, *, job)`** prepares (or reuses) and persists the job's batch under the lease fence, requires `claim_ids` to equal its candidates in order, and launches through the installation's certified route (`providers.base.complete`) or an explicit `launch`; without a route it raises `capability_unavailable` and changes nothing (candidate-only degradation). Budget reservation stays the model lane's, which prepares review jobs through the same path.
12. **Extraction** (`controller/extract.py`). Scheduled in the transaction that establishes its trigger: one job per new settled episode with steps (due after the 300 s quiet window, so its narrative usually lands first) and one per due failure trigger (`trigger_ref`). Selection is bounded: the named events and episodes, a trigger's failure and at most 24 later task events, the task, its pending boundary candidates with current binding revisions (and their first events), and at most 16 relevant claims (citing a selected event or sharing a selected failure's family first). Pending boundary candidates are **folded** here (decision 0008): extraction may return `resolve_task_binding` for them or leave them pending; they never get model jobs of their own. A selection with no explicit user request, failure or interruption, certified assertion, test/build result or pending boundary is cancelled without a call (`nothing_to_extract`). Extraction writes nothing itself; its proposal applies through `apply_proposal`.
13. **Failure debounce** (`controller/triggers.py`, ingest reducer after typed reduction, `trigger_cursor`). Deterministic in event time (occurred, else recorded), never processing time: a certified failure starts a trigger (`trig_` + SHA-256 of task and failure event); relevant events are explicit user messages, artifact changes and completed certified tool results of the same task (tool starts, telemetry, assistant text and lifecycle events do not count; the resolving success is not counted); a same-task, same-known-family success before six such events and before `failure + 600 s` resolves it (family excludes dependency fingerprints, so a changed dependency does not prevent it); otherwise it becomes due (`count` or `time`) and schedules one extraction. A repeated failure of a known family joins its pending trigger; a null family never matches a success and always starts its own trigger. The worker's sweep makes a pending trigger due once the clock passes `due_at` with no event; a success observed before the due point but ingested after the sweep still resolves a time-due trigger while its extraction is unleased (that job is cancelled, `trigger_resolved`). `expected_red` stays reserved false and never excludes a trigger. FailureRecheck against admitted lessons is Task 10.
14. **Prompts are versioned package data.** The plan's `prompts/extract_v1.md` and `prompts/review_v1.md` are shipped in the `recalith.prompts` package and loaded by it (LF-normalized), and they *are* versions `extract_claims@1` and `review_claims@1` (each followed by the shared curator rules). They replace the Task 7 placeholder texts of those two versions, which no model ever received (no route was ever certified, B1) and which no readable store can pin: schema 5 refuses every older development store (item 16). From here on a text change needs a new version: `test_prompt_digests_are_pinned_separately` pins both digests (golden values), a claim's `ModelProvenance` pins its extraction prompt digest and a `ReviewBatch` its review prompt digest.
15. **Request views of claims** (`requests.claim_for_request`). A candidate's earlier assessment is withheld; active guidance keeps the supported verdict it cannot exist without, objection text dropped. (The Task 7 view stripped every assessment, which made any request consulting active reviewed guidance invalid; it was latent until claims could become active and was found by the Task 9 kill/restart scenario.)
16. **Schema 5.** Migration `0005.sql` adds `review_requests`, `review_outcomes`, an index on `review_batches (review_job_id, created_at)`, the debounce columns `failure_sequence`, `failure_at`, `due_reason`, `resolved_by` and `job_id` on `failure_triggers`, and `trigger_cursor`; `SCHEMA_VERSION` becomes 5. A schema-4 development store is refused, never migrated silently (decisions 0007–0010; Task 17).
17. **Active guidance is superseded only by active guidance.** A supersession of an *active* claim proposed by anyone but the guarded operator must name a replacement that is itself active (reviewed, or an observed fact): an unreviewed candidate cannot retire reviewed guidance (`replacement_requires_review`, SYSTEM_SPEC §7.2). Candidates may still be superseded by candidates, and operator corrections keep their immediate effect (Task 12a).
18. **Failpoints.** `review.after_schedule`, `review.after_assessment` and `triggers.after_pass` form the `failpoints.ADMISSION` family, armed only programmatically.

## Consequences

Wired now: mapping validation, observed rendering and activation, declaration region checks, failure-body derivation, scope narrowness, strength, review scheduling/partitioning/deferral, persisted batches, assessment admission with per-candidate outcomes, `review_candidates`, extraction scheduling and selection with folded boundaries, and the debounce. Consumer-side hooks for later tasks: Task 10 owns what revalidation decides, FailureRecheck, consolidation, and the remaining semantics of narrowing, disputing and invalidating already-active guidance; Task 11 serves active guidance and candidates only as labeled uncertainty; Task 12a supplies the guarded `declare`/`correct` transports and their operator events (they reuse items 3, 7 and 9 unchanged); Task 12b fences delivery; Tasks 15/16 make the new tables participate in retention and forgetting (they hold IDs, digests and reason codes only). Semantic review of task completion statements is not built: review batches hold claims, and completion still requires cited evidence (decision 0008). No live extraction or review quality is claimed: every model behavior in the tests is a recorded proposal, and ACCEPTANCE_TESTS §5 stays unavailable until B1 clears.
