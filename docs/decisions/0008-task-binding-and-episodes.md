# Decision 0008: Typed task reduction, versioned bindings and deterministic episodes

Status: accepted (Task 6) · Date: 2026-10-17

## Context

Task 6 builds working state, binding and episodes (SYSTEM_SPEC §3.2, §3.3, §3.5, §5.2, §6.2; DATA_CONTRACTS §3, §3.1, §4, §7.1, §10, §11) on the Task 5 application path. The documents fix the rules: provisional tasks for new sessions, versioned provisional bindings, deterministic boundary candidates, the budget-independent `single_active_task` link with a linked placeholder, reversible reassignment of explicit ranges, call/result pairs that never separate, typed field patches with evidence, idle → paused, completion only with completion evidence, and episodes that never sever a failure from its later result. They leave open how a task is created through Task 5 at all (no operation kind creates one), how list items other than pending actions are closed by ID, where the reducer keeps the state its signals need, what exactly counts as activity and as a blocker, when a range becomes an episode, and how a link is reversed. Task 6 needed one answer for each. Nothing here weakens a rule; where a rule was ambiguous the stricter reading was taken.

## Decisions

1. **Controller-only operation kinds.** `create_task` (a provisional task: code-allocated `task_` ID, `new_session` or `host_reset`), `bind_events` (the first, provisional binding of unbound events plus the typed patches they support) and `record_boundary` (one pending `TaskBoundaryCandidate`) join `OperationKind`. They are in no `PURPOSE_KINDS` entry, so a model body that returns one is malformed (`kind_not_permitted`), and `apply_proposal` rejects them again (`policy.REDUCTION_KINDS`). They reach the store only through the deterministic reducer or a controller service writer, with the same admission, revision checks, atomic groups, deterministic operation IDs and `@apply` record as every other operation. `resolve_task_binding` keeps its contract payload (`TaskBindingProposal`) and is now applied (decision 0007's `task_binding_unavailable` is gone); operators may also apply it (`OPERATOR_KINDS`; the guarded transport is Task 12a).
2. **Reduction inside the fenced ingest job.** `working.reducer.reduce_ingested` is registered by default in `Worker.ingest_reducers` (decision 0006). A pass reduces every committed, not yet reduced event in commit order through the job's own events (plus at most 200 more), so jobs that run out of order still reduce in order; `working_cursor` records the last reduced commit sequence. All of it is applied with `controller.apply.apply_in_transaction` in the ingest job's fenced transaction (kind `apply_reduction`), one atomic dependency chain per application, so typed state, bindings, candidates, episodes, the cursor and job completion commit together. A refused reduction raises and fails the job (it is retried); it is never partially applied. The reducer applies as the controller actor (`typed-reducer`), whatever actor resolved the worker's context. It makes no model call and uses no budget.
3. **Bindings.** One chain per event (`bind_` + SHA-256 of the event ID) in `task_binding_revisions`, its head in `task_binding_heads` (schema 3 adds the event's commit sequence and session to the head). A result joins its call by `tool_call_id` through `tool_calls` (first start and first finish per adapter and ID), across splits and sessions; the partner's binding wins over the session's current task. Memory telemetry and operator administration events are not bound.
4. **Typed facts** (`working.tasks.fold_event`). The first explicit user request becomes the objective (`user_declared`, an exact quoted span of at most 1,024 characters) and titles a still-untitled task; a started call is a pending action `awaiting_result` with the deterministic ID `act_` + SHA-256 of adapter and call ID; a finished call closes it and records a known result (outcome, exit code, certified assertions, truncation, error signature), replacing the previous result of the same action signature (tool, working directory, argument array, paths; the raw digest when unparsed), at most 24 reducer-owned results kept; a failing test/build (`action_kind` `test`/`build`) is a blocker until the same action signature passes. Nothing deterministic sets `next_action`, constraints, plan or completion. Activity (for `last_activity_at`, idle and reactivation) is a user, assistant, tool or artifact event; session lifecycle and compaction events are not.
5. **Item IDs.** A list item that is a `SupportedText` is identified by `item_` + SHA-256 of its normalized content, so `TaskPatch(op="close", item_id=…)` can close blockers, results and the other lists, and a moved item keeps its ID. The `item` prefix is registered (wire tables regenerated).
6. **Reducer bookkeeping.** `working_sessions` holds each session's detection state (current task, provisional task, origin, last activity, the disjoint-path run, the continuity count and state); `working_tasks` holds each task's observed path clusters, the start of its open episode range, a pending-checkpoint flag and its last episode. Both are derived from events and bindings, written in the reduction transaction, never served and never advance `guidance_epoch`.
7. **Boundary signals** (`working.segment`). A pivot is a configured prefix at the very start of an explicit user message after whitespace, case-insensitive; a quoted or pasted start is no match. A pivot as a new session's first request records no candidate (the session already is a new task) but blocks the continuity link. Five consecutive path-bearing tool starts that share a cluster disjoint from the task's observed clusters propose `disjoint_paths`; actions that do not reach a candidate, and a run that did, join the task's clusters; a task's first path actions establish its clusters. Excluded from clustering: `.recalith`, `.git`, `__pycache__`, `node_modules`, virtualenv and tool caches. Operator mappings match the longest prefix first. A user message 30 minutes after the session's last activity proposes `idle_resume`. A new session proposes `new_session`, a host clear (`SessionStart` source `clear`) `host_reset`. Candidates get deterministic `bnd_` IDs and stay `pending`; the next extraction job (Task 9) reads them with `segment.pending_candidates`.
8. **The continuity link.** At a new session's third path-bearing action, with no pivot, reset or host binding before it, the reducer flushes the pass, counts nonredirected tasks of the workspace that are active or were paused within 24 hours (the head's `updated_at`), excluding the session's own provisional task, and links only when exactly one remains and all three actions lie inside its observed clusters. The link is a `record_boundary` (reason `single_active_task`) and a `resolve_task_binding` (`link_session`) applied in one atomic group: the session's range moves with provisional bindings, its typed items and pending call associations move to the target, the target's objective, constraints and narrative are untouched, and the emptied provisional head becomes `linked` with `redirect_task_id`, no pending actions and no next action. The candidate's state becomes `linked`.
9. **Binding resolution.** A proposal names exactly its events with their current binding revisions; a moved binding re-evaluates the proposal (bounded, decision 0007) and never overwrites. The events must be bound to the boundary's source task (following redirects), lie in one session, and form a contiguous slice of that session's events in the task; a range that would separate a call from a result that has already arrived is rejected (`detaches_call_result`); a call whose result is still outstanding may move and its result follows it. `confirm_split` allocates the new task, moves the range (confirmed bindings) and the items whose evidence lies wholly in it, derives the new objective from the range's first user request, keeps the source's objective, and makes the new task the session's current one when the range includes the session's latest event. `reject` confirms the events where they are. `link_session` on a pending candidate links into an eligible (active or paused, nonredirected, same workspace) task; on a `linked` candidate with the same target it confirms the deterministic link. A link is reversed by an explicit `confirm_split`, which creates a new task and never revives the placeholder; a linked candidate cannot be rejected.
10. **Completion.** An `update_task` status patch to `completed` needs a `completion_basis` citing at least one record, in the same operation or already on the head (`completion_requires_evidence`). Idle tasks are paused by the worker after `worker.paused_task_hours` (24) without activity, through an `update_task` status patch; new activity reactivates a paused task; neither path ever completes one. Whether a cited completion statement concerns the stated objective is semantic review (Task 9).
11. **Episodes.** A task's open range is its bound events not yet in one of its episodes. Checkpoints are compaction events, session end and an idle pause. At a checkpoint the range becomes a `settled` episode unless a test/build in it still fails (its latest outcome in the range) or, except at session end, a call still awaits its result; then the checkpoint stays pending and is taken when the range resolves. A range of 64 tool steps becomes an episode regardless, `open` when unresolved; the next episode relates to it and carries its unresolved items as preconditions. `CreateEpisodePayload` gains `state` (`open|settled`) and `EpisodePatch` may set `state` to `open|settled` (archiving stays code-owned); `create_episode` coverage is computed by code from the source events. Condensation keeps each result's outcome, exit code, certified assertions, error signature and an exact excerpt of up to 240 characters with its locator; later user messages are steps; links to events outside the episode, including the objective's, use relation `context`; every `causal_assessment` is null until a model narrative revises it.
12. **Undo.** Binding entries are recorded on their operations; an operator undo restores a binding whose head is still the revision the operation wrote (an initial binding is never undone) and returns the candidate it decided to its earlier state; later changes are conflicts, as in decision 0007.
13. **Narrative scheduling.** Typed reduction does not enqueue `update_task` or `build_episode` model jobs: their requests need the production request preparer (Task 7, `prepare_model_request`), and weak boundary candidates fold into extraction jobs (Task 9). Recorded proposals for both purposes apply through `apply_proposal` today.
14. **Failpoints.** `reduce.after_apply` (in the ingest job's transaction after the reducer's first application) and `binding.after_rebind` (inside a binding resolution after the range is rebound) form the new `failpoints.REDUCTION` family. Nothing arms them outside a test process.
15. **Schema 3.** Migration `0003.sql` adds the binding-head columns and indexes, `tool_calls`, `working_cursor`, `working_sessions`, `working_tasks` and indexes on task heads, boundaries and episode heads; `SCHEMA_VERSION` becomes 3. A schema-2 development store is refused, never migrated silently (decision 0007; the upgrade path is Task 17).

## Consequences

Task 7 supplies the request preparer for `update_task`/`build_episode` narrative and decides their scheduling within the ordinary budget; its requests carry task state, episodes and pending candidates. Task 9 adds FailureTrigger debounce (A66), extraction that folds pending boundary candidates into its job, claim extraction and semantic review of completion and of A13 lessons. Task 10 consolidates settled episodes. Task 11 and Task 12b serve task state, follow `redirect_task_id`, and expose provisional status. Task 15/16 make the new tables participate in retention and forgetting. Strict optimistic concurrency means a model narrative patch prepared against an older task revision is re-evaluated when typed reduction advances the task meanwhile (bounded to three re-evaluations); scheduling narrative at checkpoints, when a task is quiet, is Task 7's to decide. Live segmentation and narrative quality are measured in ACCEPTANCE_TESTS §5, not by these mechanics tests.
