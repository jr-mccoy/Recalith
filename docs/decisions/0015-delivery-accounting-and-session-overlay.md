# Decision 0015: Delivery accounting, the session overlay and corrections at the fence

Status: accepted (Task 12b) · Date: 2026-10-19 · Host observed: Claude Code 2.1.301 fixtures (capture; request-capture delivery feasibility from Task 0b); installed CLI 2.1.303; no live route (B1)

## Context

Task 12b adds the delivery branch to the hook (SYSTEM_SPEC §5.1.1–§5.1.2, §8.2–§8.3, §9.3; DATA_CONTRACTS §2.3, §9–§11; ACCEPTANCE_TESTS A24–A27, A41, A58, A59, A72) on the Task 11 stdlib compiler (`fast.cache.compile_packet`, its fence) and the Task 12a guarded corrections. The documents fix the rules: hooks never write SQLite and receipts travel through the spool; a per-session scratch of at most 128 KiB, 256 entries and 32 outcomes under a lock waited for at most 20 ms with atomic replace; reserve before stdout, mark after flush, a crash in between leaves an uncertain still-charged attempt; suppression from emitted entries plus ingested receipts keyed by `(record_id, revision, condition_digest, purpose_class)`; eviction never resets totals; one restoration per compaction event within 2,000; one shared 400-token substitution for a prompt when pre-action injection is unavailable; the fence is the linearization point and output in flight after it is recorded, never claimed retractable; delivery is gated by the installed capability manifest. They leave open how a manifest names the installed paths, where the per-attempt facts live so a later hook can account a dead one, how a scratch total and the durable receipts combine, what a condition digest covers, which restoration key identifies a compaction on 2.1.301 (whose `SessionStart(compact)` arrives before `PostCompact`), what a restoration repeats, where the substituted caution's action comes from when no pre-action packet can be injected, what the overlay may change, what an outcome link's label may claim, and where the delivery tables need columns. Task 12b needed one answer for each. Nothing here weakens a rule; where a rule was ambiguous the stricter reading was taken.

## Decisions

1. **Gating (context_schema 3).** The hook-context manifest's adapter entry is `{host_version, delivery_enabled, delivery_paths}`; `delivery_paths` ⊆ `session_start|prompt|pre_action|compact_restore`, empty unless `delivery_enabled`. The hook delivers only for an installed path and only when the recorded host version is certified for the adapter (2.1.301); any other version is `host_version_uncertified` (conservative capture). Schemas 1 and 2 still capture and never deliver. `capture.hooks.write_hook_context(..., delivery_paths=)` is the only writer; in this build only controlled test manifests pass paths. Task 13's `integrate` enables certified paths for a real host after the nonce protocol; a hook writing a context envelope is local emission, never a delivery certification. The hook reads no `project.toml`, so the unchanged-memory allowance is the specified default 4,000 (`ContextBudgetConfig.unchanged_session_total`); packet budgets are Task 11's.
2. **One delivery (`fast/delivery.py`).** Purpose from the registered role: `SessionStart` (startup/resume/clear) → `session_start`, `SessionStart(compact)` → `compact_restore`, a user prompt → `prompt` (or the pending restoration, item 7), `PreToolUse` → `pre_action`; anything else delivers nothing. Order under the shared deadline: capture, delivery, worker start, overlay. Delivery compiles first (views or ≤32 fallback rows; Task 11), then takes the session lock (≤20 ms and the remaining time; a timeout or an unsupported lock skips delivery, never capture), reads scratch and — in a fresh read-only snapshot — the session's durable receipts, then reserves, fences, emits, spools the receipt and marks, all under the lock. Without at least 40 ms left it does nothing (`deadline_delivery_skipped`). The query carries the adapter's platform `os`/`arch` (merged over the worker's resolved environment in both compilers), the branch read from `<workspace>/.git/HEAD` (one bounded no-follow read; a linked worktree, a detached head or anything unreadable is unknown; git never runs) and, for a pre-action, the captured action.
3. **Scratch (`fast/session.py`).** Each entry holds what a later hook needs to spool its receipt: packet digest, emitted items, purpose, estimate and substitution portion, task, restoration key, trigger event, generation time, the fence epochs and store revision, emission/fence times, the post-emission check and `receipt_spooled`. The scratch adds `restoration_tokens` (the restoration part of `reserved_tokens`), the open `compaction_key` and up to 32 `restored` keys. Fields have defaults, so `scratch_schema` stays 1. An invalid file is never trusted: the hook starts from an empty scratch (`scratch_invalid`) and floors totals with the durable receipts.
4. **Charging.** The unchanged-memory charge is `max(scratch.reserved − scratch.restoration, Σ durable ordinary rows + Σ scratch ordinary attempts not yet durable)`, attempts counted once by ID. A packet is first fitted to its own caps; then ordinary items drop from the end until it fits the remaining allowance; a caution, a conflict or a changed revision (`why[0] = revision_change`) may exceed the allowance within its packet cap; the whole estimate, substitution included, is charged. A restoration is charged to `restoration_tokens`, outside the allowance. At capacity (256 entries or the 128 KiB cap less 16 KiB headroom) the hook drops only entries whose receipts the worker has durably accounted (verified read-only; the "worker-owned safe checkpoint" is the worker's accounting row, not a worker write to scratch); if that frees nothing it withholds output (`scratch_capacity`). Counters never go down, except that a reservation the fence refused is withdrawn: provably nothing reached stdout.
5. **Attempts.** Reservation (`reserved`) is written before any byte reaches stdout; after the flush a fresh snapshot records `in_flight_change` (did the guidance, policy or tombstone epoch move after the fence?), the emitted receipt is spooled, then the entry is marked `emitted`. A hook that finds a `reserved` entry under the lock knows its owner died (the owner holds the lock until its mark) and turns it `uncertain`: still charged, never seen, its receipt spooled. A failed stdout write is `uncertain` at once. A receipt the spool refused is re-spooled by later hooks (at most 4 per hook, with ≥100 ms left) and at session end, which settles every owed receipt before discarding the scratch (otherwise the scratch is kept). Exactly-once stdout is not promised.
6. **Suppression.** `condition_digest` (shared `fast.context.condition_digest`) covers the advice and tri-state applicability as decided, freshness, each condition's result with the current value it compared (environment and version keys, the branch, the action kind or tool; paths by result only), each scope dimension's result and scope environment values, the bounded live dependency values (unknown is `None`) and, for an open question, its members' revisions. Keys come from emitted scratch entries and ingested emitted receipts only. The purpose class is `ordinary` for start, prompt and pre-action and `restore:<key>` for a restoration, so a question or a caution is delivered once per session across purposes, and a restoration repeats what compaction removed. A changed revision of a record emitted earlier in the session resurfaces as `revision_change`. An open intent question is one conflict item; its key changes with its members' revisions, so a changed question resurfaces and an unchanged one does not repeat.
7. **Restoration.** A captured compaction opens a cycle in scratch: `pre` (`PreCompact`) always opens one keyed by its event ID; `post`/`context_restored` open one only when none is open, so on 2.1.301 (`PreCompact`, `SessionStart(compact)`, `PostCompact`) one compaction has one key. With the `compact_restore` path the `SessionStart(compact)` hook restores; without it the next prompt on a certified prompt path takes the `compact_restore` purpose once. The key is recorded at reservation (restore once, even if that attempt ends uncertain). A restoration packet keeps its 2,000 cap with any caution inside it (no substitution); it is relevant through the session's earlier emitted records (`compaction_restore`, a hook-only compiler input) besides Task 11's relevance. A second compaction without a `PreCompact` (auto-compaction, not observed headless) is not restored: ordinary limits apply rather than a guessed allowance.
8. **Substitution.** When `pre_action` is not installed, a prompt compiles with Task 11's `substitute_pre_action` and with the session's latest typed outcome's action (from the overlay) as its action, so an eligible action-specific caution can ride the one shared ≤400 allowance (≤1,400 total). No action, no caution, no bonus; never per caution or per queued tool.
9. **The overlay.** A post-tool hook records the typed outcome (Task 3b). At delivery, up to two recent failures relevant to this delivery (a pre-action: the same exact action family or an overlapping path; a prompt or restoration: the latest) are labeled `recent_observation` context items keyed by their event, before any ingestion; a later success of a caution's action family, or a changed path among its dependencies, downgrades that caution to context with the reason (the store's FailureRecheck then follows at ingestion). Overlay items are fenced as events that may still be absent from the store; once ingested they must hold available evidence. A policy or tombstone epoch mismatch clears the overlay content (`scratch_epoch_reset`), never the totals. Nothing in the overlay is a lesson or support.
10. **Fence and in-flight output.** The final fence runs after the reservation, on a fresh snapshot, immediately before the write: a change committed before it (a guarded `recalith correct`, an undo, a recheck, a forget) excludes the old text and the reservation is withdrawn (`fence_epoch_changed`/`fence_record_changed`); a change committed after it may race output already started, and the receipt records `fenced_at`, `emitted_at` and `in_flight_change`. Nothing claims retraction.
11. **Receipts and accounting (schema 8).** A receipt is a `memory_delivered` event (memory channel, derived, no root) keyed `delivery:<attempt>:<state>`, with `delivery_id = dlv_` + the attempt's UUID body. `DeliveryReceipt` gains `restoration_key`, `trigger_event_id`, `fenced_at`, `in_flight_change`. Ingestion (`retrieval.delivery.account`, inside the event's transaction) inserts one `deliveries` row per attempt; an emitted receipt upgrades an uncertain row, an uncertain one never downgrades an emitted row; bookkeeping only (the guidance epoch does not move). Migration `0008.sql` adds `host_id`, `restoration_key`, `trigger_event_id`, `fenced_at`, `in_flight_change`, `receipt_event_id` and indexes; `SCHEMA_VERSION` 8; a schema-7 development store is refused, never migrated silently (decisions 0007–0014; Task 17). The service `record_delivery(ctx, packet, session_id)` spools the same receipt shape through `capture` (condition digests from the caller, else from the item's own advice/applicability/freshness/conditions); the hook uses only the stdlib `hook_record_delivery`.
12. **Outcome links.** Ingestion links an emitted delivery to observed follow-up events: a pre-action delivery to its call's `tool_finished` (labeled `task_failed`/`task_succeeded` only from a certified result of a `test` action, else `unknown`), and any emitted delivery of the session to an assistant message citing an emitted record ID (`acknowledged`). Links change no claim, strength, root or evidence; an acknowledgment is never support or task success; `action_changed` is not assigned automatically in preview.
13. **Failpoints.** `delivery.after_reserve`, `delivery.after_fence`, `delivery.after_emit`, `delivery.after_receipt`, `delivery.after_mark` form `failpoints.DELIVERY` (armed only programmatically).

## Consequences

Wired now: the delivery branch of `handle_hook` for the four purposes, scratch reservations and totals, suppression keys, question deduplication, restoration and substitution, the overlay at delivery, the final fence with in-flight recording, receipts through the spool, worker accounting and outcome links, the service `record_delivery`. Consumer-side hooks for later tasks: Task 13 certifies paths with the nonce protocol against the real engine and writes `delivery_paths` through `integrate`, and adds host command rules; Tasks 15/16 must purge `deliveries`/`outcome_links` rows and scratch files with forgotten records (forgetting already advances the tombstone epoch that clears overlay content; the files themselves must be purged) and include receipts in retention; Task 17 reports delivery outcomes, degradations, `in_flight_change` counts and uncertain attempts in health. Limits: the allowance is the default constant until a hook-readable budget exists; an auto-compaction without `PreCompact` is not restored; a resumed session whose last receipts are still in the spool when its scratch was discarded can undercount until ingestion; outcome labels are telemetry. No delivery certification, live recall quality or live agent outcome is claimed (B1).
