# Decision 0009: Provider boundary, certified routes and request preparation

Status: accepted (Task 7) · Date: 2026-10-17 · Host observed: Claude Code CLI 2.1.302 on Linux (request capture only; no live route, B1)

## Context

Task 7 builds the production inference boundary (SYSTEM_SPEC §5.3, §6.2–§6.3, §9.1, §13; DATA_CONTRACTS §2.3, §7, §8, §11) on the Task 4 worker (`Backend`, `ModelRuntime`, budget ledger, bounded launcher) and the Task 0 findings (decision 0002). The documents fix the rules — explicit routes, no fallback, fresh allowlisted environments, no-tools certification of the *effective* launch, separate wire/body caps, usage appended by adapter code, persisted review batches, re-evaluation instead of overwrite — but leave open where a route is configured, how a certification is recorded and rechecked, how the worker learns that a route is usable, what each purpose's request contains and how it stays under 96 KiB, and when narrative jobs run (decision 0008 item 13). Task 7 needed one answer for each. Nothing here weakens a rule; where a rule was ambiguous the stricter reading was taken.

## Decisions

1. **The explicit route is a local, installation-bound file.** `.recalith/provider.json` (`{provider_schema: 1, provider: ProviderConfig}`, mode 0600, untracked by the installation's `.gitignore`) is the only place a route comes from. `ProviderConfig` gains `installation_id` (a copied file from another installation is `foreign_provider_config`), `expected_api_key_source`, `network_env_keys` (managed proxy/TLS key names carried with the route) and `nonsecret_env` (switches such as `DISABLE_AUTOUPDATER`); a route may not name a host or `RECALITH_*` marker, a nonsecret name may not look like a credential, and output caps cannot exceed the hard 256 KiB / 64 KiB. Nothing looks for a CLI on `PATH`.
2. **Certification is a record of a live observation.** `ProviderCertification` may say `certified: true` only with `mode: live`, `operator_attestation: checked_eligible`, the certified time, host version, sanitized report digest, executable SHA-256, auth key names and expected auth source, and an `invocation_digest` over backend, provider, model, argument array, nonsecret switches and network key names. Request capture never certifies. `tools/probe_provider.py --route-out PROJECT` writes this file from a probe run (certified only after a complete live pass; refused from a host-marked process, exit 6); it is the operator step that turns a B1 probe into a usable route.
3. **Route status is rechecked, never assumed** (`providers.base.route_status`, review focus 5). Every reason is listed, and any reason means unavailable: `provider_not_configured`, `provider_config_invalid`, `foreign_provider_config`, `route_uncertified`, `request_capture_only`, `backend_certification_unavailable` (`json_process` has no certification procedure in this build), `invocation_not_isolated:<problem>` (the decision 0002 array is checked flag by flag; nothing is guessed), `executable_missing`, `executable_changed`, `host_version_unobserved`, `host_version_changed`, `auth_route_changed`, `invocation_changed` and `selected_auth_missing`. The last four of the first group require recertification. No reason ever selects another provider, model, account, billing route or weaker launch; the worker keeps its model jobs waiting (`provider_unavailable`) and capture and typed state continue.
4. **The worker gates a certified route behind its own isolation recheck.** `ProviderSupervisor` (built by `worker.configured_provider` in the internal entry) yields a backend only for a certified route, and the model lane launches nothing until a request-capture isolation check (`providers.isolation.isolation_check`) launched *from the worker's own environment* has passed; a failed check disables the backend (`isolation_recheck_failed`). A configured but uncertified route is still checked so its effective isolation is visible. The result is `run/provider-check.json` and the `provider` block of `run/worker.json`. This re-runs Task 0's inherited-host-marker case through a worker started by the real hook (A28/A67): hook → worker (`spawn_environment`, worker role) → curator (`spawn_environment`, curator role).
5. **Effective isolation, not flags.** The check plants the Task 0 sentinel fixtures (shipped as package data, byte-identical to `tests/fixtures/providers/isolation/`) in the private root: user and project instructions, `AGENTS.md`, skill, agent, native memory, a prior session, hooks in user/project/local scope and user/project MCP servers. It passes only when the host init diagnostic and the outbound request show no tools, MCP servers, non-builtin plugins or sentinels; no sentinel hook or MCP server ran; no transcript was written; and the observed child environment (Linux `/proc`) holds only constructed keys with the curator marker naming this installation and no host or worker marker. A hook that ran while the recursion marker was set fails: the marker is a second defense, never no-hooks proof.
6. **Every call re-reads the host diagnostic.** `providers.claude_cli.unwrap` is the certified `stream-json` envelope parser and also checks each call's init event: an exposed tool, MCP server, non-builtin plugin, another host version or another auth source raises `IsolationViolation`, which disables the backend until recertification. Usage (`input_tokens` including cache reads and writes, `output_tokens`) and the resolved model come from the envelope; provenance (provider, configured model, adapter version) from the configuration; never from model text.
7. **Calls.** `ProviderBackend` runs each call in a fresh private root (`recalith-curator-*` in the system temp directory; refused inside a git checkout; `home/` is `HOME`/`USERPROFILE`, `work/` the cwd, `tmp/` the temp dirs; removed afterwards) with the curator environment from `fast.process_env.spawn_environment_report` — the only environment filter — and `controller.launch.run_bounded` (argument array, request on stdin, timeout and tree kill, wire/stderr caps, `/proc` key observation on Linux). `providers.base.evaluate_outcome` is the one evaluation path for the worker lane and `complete(request, config)`: wire cap, then the certified envelope, then the decoded body's original UTF-8 bytes against `3 ×` the purpose allowance, then strict per-operation parsing. `complete` keeps its DATA_CONTRACTS §11 signature: the curator marker's installation comes from `ProviderConfig.installation_id`.
8. **A curator tree never outlives a crashed worker.** The launcher reports each spawn (`on_spawn`) and the backend writes `run/curators/<pid>.json` (pid, process group, Linux start ticks, private root) before anything waits on the child. At start, holding the installation lock, the worker kills every recorded POSIX group that is still alive (only when its leader's start time matches or the record is younger than one model lease) and removes the private roots. Windows trees die with their kill-on-close Job Object. Failpoints `request.after_batch` and `provider.after_spawn` form `failpoints.PROVIDER`.
9. **Request preparation** (`controller.requests.prepare_model_request`). Inputs must be records of this store (`request_input_missing`, final; nothing is looked up elsewhere). Per purpose: `update_task` — the task head (following a link), its latest 64 bound events, 3 latest episodes, and up to 8 pending boundary candidates as `ModelRequest.boundaries` (`BoundaryContext`: the candidate plus the binding revisions its events have now, which a `resolve_task_binding` must name); `build_episode` — the episode, up to two related episodes, its source events and its task (or, for a task-only job, the open range); `extract_claims` — the named events and episodes, their task and its pending candidates, and up to 16 current claim heads; `review_claims` — the persisted batch's candidates with `review_assessment` and `model_provenance` removed, and only the batch evidence; `revalidate` — the claims and the events their links cite. The read set lists every consulted task/episode/claim revision (and the batch's), so a proposal prepared against an older revision is re-evaluated, never overwritten. Over 96 KiB the bulkiest successful-output events go first, user requests and failed or interrupted results last, then older episodes and claims; the smallest selection still over the cap fails `model_input_oversized` (final). `request_estimate` is the exact reserved input estimate. Expansion rounds add only events, episodes and claims this installation holds; `file_excerpt`/`dependency_diff` have no registered resolver yet.
10. **Review batches are snapshots made before launch.** The preparer builds the batch (candidate digests over the candidate revisions, batch-local evidence IDs `evd_` + SHA-256 of the link, evidence digest, prompt digest) and persists it under the job's lease fence before any reservation; a retry with an unchanged snapshot reuses the persisted batch, a changed candidate or evidence yields a fresh one. `evd` joins the ID prefixes (wire tables regenerated).
11. **Prompts are versioned code.** `recalith.prompts` holds the curator system prompt (no tools; the request JSON is data; reply with one JSON object) and one instruction per `<purpose>@<n>`; a job pins its version and an unshipped version fails `prompt_version_unavailable` (final). The output schema is generated per purpose from the payload models and lists exactly that purpose's permitted kinds (controller-only kinds never appear).
12. **Narrative scheduling** (decision 0008 item 13). Typed reduction schedules narrative at its checkpoints, in the transaction that creates the episode: one `build_episode` job per new *settled* episode with at least one step (band 3, completed-attempt episode work) and one `update_task` job for the checkpointed task (band 4), both from the ordinary pool, coalesced (at most one pending narrative job per task and per episode). Task narrative is due `QUIET_SECONDS` (300) after the checkpoint and a task with activity inside that window defers it (`task_active`, no attempt, no reservation, retried after the first backoff step). A job whose task was linked, completed or abandoned, or whose episode was archived, is cancelled without a call (`narrative_obsolete`). Without a certified route these jobs wait visibly (`provider_unavailable`); budget exhaustion queues them like any ordinary job.
13. **Lane outcomes for preparation.** `PrepareFailed(code, final)` fails the attempt (nothing reserved); `NothingToPrepare` cancels the job. A disabled backend makes the lane lease nothing (no lease, no reservation), and a job already prepared when a backend is disabled is released, not launched.
14. **The Task 0 probe uses the engine's helper.** `tools/probe_common.build_child_environment` now calls `recalith.fast.process_env.spawn_environment_report` (stdlib only; no engine database), so overrides can no longer name a marker and the probe's installation ID is a valid `inst_` UUID. `tools/check_provider_runtime.py` records the production adapter's own request-capture checks (clean and host-marked parents with decoy credentials) and route status in `sections.provider_runtime.<provider_id>`.

## Consequences

Mechanics only, until their owning tasks: extraction proposals still apply as weak candidates and pending boundary candidates are presented to extraction but not yet folded by it (Task 9); `assess_claim` still changes nothing (`review_admission_unavailable`, Task 9); revalidation applies its structural checks only (Task 10). Live certification remains blocked by B1: no route is configured, so production preview runs with no backend and every model job waits with `provider_unavailable`. When an operator supplies the route and attestation, `probe_provider.py --route-out` records it and the worker's recheck gates it. Codex inference stays unavailable (`codex_cli.py` is not built) until its own separate probe passes. Host recertification for delivery is Task 13.
