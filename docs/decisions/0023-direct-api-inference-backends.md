# Decision 0023: Direct-API inference backends

Status: accepted (Task 7 follow-up) · Date: 2026-10-22 · Observed: loopback request capture only (no provider account, no real network call; B1 still open)

## Context

Until now the only certifiable inference route was `claude_cli`: `claude -p --bare` with an Anthropic API key, an `apiKeyHelper` or cloud credentials (decisions 0002, 0009). The generic `json_process` backend stays uncertifiable (`backend_certification_unavailable`) because an arbitrary executable exposes no diagnostic from which its tool and customization isolation could be established. An operator who has an API key for another provider, an Anthropic key funded by a plan's included API credits, or a local OpenAI-compatible server had no route.

A direct HTTPS call to a model API has no agent harness: no tools, hooks, MCP servers, instruction files, settings, plugins or native memory exist on the client side. Its isolation reduces to one checkable statement: *the engine sent exactly this request, with no tool definitions and no state, using only the selected key*. A loopback capture of the actual bytes on the wire can prove that. SYSTEM_SPEC §9.1 already anticipates more backends ("a generic configured JSON process backend can support a local model adapter later"; "do not hardcode a particular frontier model name"). This decision adds two backends Recalith ships itself, and states how they are configured, called, certified, rechecked and reported. Nothing here relaxes a rule: where a provider cannot meet one, it is not certifiable, and the gap is recorded.

## Decisions

1. **Backend kinds.** `ProviderConfig.backend` gains two values. Each is an adapter shipped in `recalith.providers`, never a user-supplied executable.
   - `anthropic_messages`: the Anthropic Messages API, dialect `messages` (`POST …/v1/messages`). Bedrock and Vertex are **not** shipped: their request shapes, endpoints and authentication (SigV4, Google OAuth) differ, and each would need its own certified dialect.
   - `openai_compatible`: dialect `chat_completions` (`POST …/chat/completions`) only. It is the one dialect that OpenAI, Azure OpenAI, OpenRouter, Groq, Together, Gemini's OpenAI-compatible endpoint, Ollama, LM Studio and vLLM all serve. The Responses API is not shipped: it stores responses server-side by default and offers conversation state and built-in tools, so it adds state the engine would have to switch off and prove off, and few compatible servers speak it. It can be added later as its own dialect with its own capture tests.
   - Native Gemini (`generateContent`) is not shipped; Gemini is reachable through its OpenAI-compatible endpoint, which the operator certifies like any other.
2. **Process model.** Each call runs the Recalith-owned stdlib transport `src/recalith/providers/http_transport.py` as a child, `python -I <path>` with the worker's own interpreter, through `controller.launch.run_bounded`. The existing timeout and process-tree kill, the 256 KiB wire and 64 KiB stderr caps, the curator role environment (`fast.process_env.spawn_environment`), the per-call private root, the spawn record and crash reaping (decision 0009 item 8) all apply unchanged. The child is a transport only: the engine builds the complete request in the parent (method, URL, header names and values except the credential, the exact body bytes); the child reads that specification on stdin, adds the credential from its own environment by the configured key name, sends it once, and writes one header line plus the raw response body to stdout. It imports only the standard library (`urllib.request`, `http.client`, `ssl`), never `recalith`, so `-I` with its file path needs no package import. No new runtime dependency is added.
   - TLS: `ssl.create_default_context()` with system trust; a managed CA bundle reaches it only as `SSL_CERT_FILE`/`SSL_CERT_DIR` in `network_env_keys`. There is no option that disables verification or hostname checking, and the source is audited for one.
   - Proxies come only from the curator environment (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` named in `network_env_keys`), read with `urllib.request.getproxies_environment`; the platform's system proxy settings (Windows registry, macOS SystemConfiguration) are never consulted. Redirects are never followed (a 3xx is a failed call), so a credential cannot be carried to another origin.
   - `http://` is accepted only for a loopback host (`127.0.0.1`, `::1`, `localhost`), in the configuration validator and again in the child.
3. **Contract changes** (DATA_CONTRACTS §11, `contracts/config.py`).
   - `ProviderConfig.backend`: `claude_cli | json_process | anthropic_messages | openai_compatible`.
   - `executable` and `invocation_args` apply to process backends only; an API backend has `executable: null` and an empty `invocation_args`.
   - New `ProviderConfig.endpoint: ApiEndpoint | null`, required exactly for API backends: `url` (https, or http for loopback; no user info, no fragment, no credential-shaped query), `dialect` (`messages` for `anthropic_messages`, `chat_completions` for `openai_compatible`), `auth_header` (`x-api-key`, `authorization_bearer`, `api-key` for Azure, or `none`), `output_cap_field` (`max_tokens` or `max_completion_tokens`; Messages requires `max_tokens`), `json_mode` (`none` or `json_object`; Messages requires `none`) and `api_version` (the `anthropic-version` header value, required for Messages and absent otherwise).
   - New `ProviderConfig.expected_resolved_model`: the model identifier the provider must report back when it differs from the one sent (an Azure deployment name, a provider alias). Null means the reported model must equal `configured_model`.
   - `AuthRouteKind` gains `none`, permitted only with `auth_header: none`, no auth keys and a loopback endpoint.
   - Keys remain environment-variable *names*; values are never stored. `installation_id` binding (`foreign_provider_config`), `expected_api_key_source` (Claude CLI only), the output caps, `network_env_keys`, `nonsecret_env` and the no-fallback rule are unchanged.
   - `ProviderCertification` gains `resolved_model` (required when an API route is certified), `failed_checks` (the checks a non-passing probe run failed, listed by `route_status` as `certification_failed:<check>`) and the attestation value `not_applicable_local` (only for a loopback endpoint). Backend-specific completeness moves to `ProviderConfig`: a certified Claude CLI route still records its host version, checked eligibility and auth key names. No store or migration change.
4. **Mandatory request properties.** The engine builds every request itself; the dialect modules (`providers/api.py`) are the only code that shapes one.
   - The pinned model, sent as `model`.
   - A hard output-token limit equal to the purpose's reserved output allowance (SYSTEM_SPEC §6.3: 1,500, 8,000, 8,000, 3,000, 3,000), sent as `max_tokens` (Messages) or the configured `output_cap_field` (Chat Completions). A provider or endpoint that cannot enforce the limit is not certifiable: the live certification observes it (item 7) and records `output_cap_unenforced` or `output_cap_unobserved`; the rule is never relaxed. A reported output count above the cap on any later call is a route violation that disables the backend (`output_cap_exceeded`).
   - No `tools`, `tool_choice`, `functions`, `function_call`, `parallel_tool_calls`, `stream`, `n`, `store`, `metadata`, `previous_response_id` or any other key: the body's key set is exactly the dialect's expected set. Chat Completions keeps no conversation state; OpenAI's `store` defaults to false and is not sent, so a strict compatible server does not reject an unknown field. The transport makes exactly one attempt; the engine's backoff is the only retry. A server-side retry or routing inside an aggregator is not visible to any client and is recorded as a gap (item 10).
   - The curator system prompt (`recalith.prompts.CURATOR_SYSTEM_PROMPT`) as the system text (`system` for Messages, a `system` message for Chat Completions) and the canonical `ModelRequest` JSON exactly as today as the single user message.
5. **Structured output** (verified against the official documentation, SOURCES_AND_REUSE §4).
   - Messages: no native JSON-object mode exists. Native structured output (`output_config.format` with a JSON schema) is not used: it adds a provider-written system prompt the engine cannot see, and it rejects the constraints the engine's per-purpose `output_schema` uses (`maxLength`, numeric bounds, `additionalProperties` other than false), so the schema would have to be rewritten into a weaker one. The request asks for JSON in the curator system prompt and carries `output_schema` in the request body, exactly as the certified Claude CLI route does.
   - Chat Completions: `response_format: {"type": "json_object"}` by default (`json_mode: json_object`). It adds no model-visible tool; it requires the word JSON in the context, which the curator system prompt contains. Strict `json_schema` mode is not used for the same reason as above (every field must be required and several keywords are unsupported). `json_mode: none` exists for servers that reject `json_object`; the live certification decides which one a route uses, and the choice is pinned in the invocation digest.
   - Either way the engine's strict per-operation parsing (`controller.budgets.decode_purpose_body`) stays the authority; a native mode is never a reason to trust a body.
6. **Responses, usage and provenance.**
   - Messages: success is HTTP 200, `type: message`, exactly one `text` content block, `stop_reason: end_turn`. `max_tokens` and `model_context_window_exceeded` fail as `output_cap_reached`; `refusal` fails as `provider_refused`; a `tool_use` block or `stop_reason` `tool_use`/`pause_turn` is an isolation violation (`isolation_tools_exposed`) that disables the backend. Usage: input is `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` (the Claude CLI route's sum), output is `output_tokens`.
   - Chat Completions: success is HTTP 200 with exactly one choice whose message has string content, no `refusal`, no `tool_calls`/`function_call`, and `finish_reason: stop`. `length` fails as `output_cap_reached`; `content_filter` or a refusal as `provider_refused`; tool calls as `isolation_tools_exposed`. Usage: input `prompt_tokens` (cached tokens are a subset), output `completion_tokens` (reasoning tokens are a subset).
   - Missing or non-integer usage is unknown, so the engine's estimates are charged (local servers may report none). The response `id` is the provider request ID.
   - The returned `model` must equal `expected_resolved_model` (or `configured_model`); a different one is never a silent substitution: the call fails and the backend is disabled (`model_mismatch`) until the route is recertified. It is recorded as `resolved_model` in the provenance, as today.
   - HTTP failures map onto the existing failure path (charged, normal backoff): 400 `provider_request_rejected`, 401/403 `provider_auth_rejected` (disables the backend), 404 `provider_not_found` (disables the backend), 408/504 `provider_timeout`, 413 `provider_request_too_large`, 429 `provider_rate_limited`, 529 `provider_overloaded`, other 5xx `provider_server_error`, 3xx `provider_redirect_refused` (disables the backend), anything else `provider_failed`. Transport failures: `endpoint_unreachable` (refused, DNS, reset), `tls_verification_failed`, `provider_timeout`. Budgets reserve before launch and charge every failed attempt, as before.
7. **Certification** (in place of the CLI's sentinel-file check, which has nothing to plant for a direct call).
   - **Request capture** (`providers.isolation.isolation_check`, API branch): the engine points the transport at a loopback capture endpoint (same path and query as the configured URL), with a placeholder value under the selected key name, and verifies the bytes received: method `POST`; path and query; the exact header-name set; the credential only in the configured header and scheme and equal to the placeholder; no value of any other credential-shaped inherited variable anywhere in the request; a body byte-identical to the one the engine built, whose keys are exactly the dialect's set (no tool fields), with the pinned model, the output cap, the JSON mode, the curator system prompt and the request JSON. The capture's reply is then parsed by the production `unwrap`. The child's observed environment (Linux `/proc`) must hold only constructed keys and the curator marker, with no host or worker marker. Request capture never certifies.
   - **Recheck before use**: the worker repeats this check from its own environment before its model lane launches anything (decision 0009 item 4, unchanged), so a route copied into a worker whose environment differs is withdrawn (`isolation_recheck_failed`).
   - **Live certification**: `tools/probe_provider.py` with the API backend, run by the operator from an ordinary terminal with their own key, from a clean and a host-marked parent. It passes only when: the request-capture checks and the bounds (hang, flood, oversized and malformed bodies) pass; the call authenticates; the reported model equals the expected one; a schema-valid no-op body comes back within the timeout; a deliberately small cap is enforced (the call stops with the cap reason and any reported output count is within it); the endpoint is the configured origin (no redirect; verified TLS unless loopback); and the operator attests the provider's terms (`checked_eligible`), or `not_applicable_local` for a loopback server. Usage reporting is recorded (reported or unknown), not required. Only that run writes `certified: true` (`--route-out`).
   - **Invocation digest** for API backends: backend, provider ID, configured model, expected resolved model, the whole `endpoint` (URL, dialect, auth header, output-cap field, JSON mode, API version), the auth key names, nonsecret switches and network key names. `executable_sha256` records the SHA-256 of the shipped adapter sources (`http_transport.py` and `api.py`), so an engine whose adapter changed reports `adapter_changed` and needs recertification. Claude CLI routes keep their digest unchanged.
8. **Local servers.** A loopback `http` endpoint is allowed with `auth_route: none` or with a key. It has no provider terms (`not_applicable_local`) but still needs the live certification of the output cap, the JSON body and the model identity; unknown usage means engine estimates are charged.
9. **Route status and health.** `route_status` lists every reason, as before; API backends add `adapter_changed` and `certification_failed:<check>`, never observe a host version, and never report `executable_missing`. The backend's own call outcomes add `model_mismatch`, `output_cap_exceeded`, `provider_auth_rejected`, `provider_not_found` and `provider_redirect_refused` (each withdraws the route until recertification or a worker restart) and the last transient failure (`endpoint_unreachable`, `tls_verification_failed`, `provider_rate_limited`, …), which `recalith status` shows as a degraded inference reason. `json_process` stays `backend_certification_unavailable`. Reports carry key names only; the transport never prints a key, a header value or a response body to stderr. The registered hook start now forwards the route's `network_env_keys` to the worker as well as its auth keys, so a proxy or CA bundle the route needs reaches the curator.
10. **Known gaps.** An aggregator (OpenRouter and similar) may route one model across hosts server-side; only the reported model is checkable. Compatible servers differ in which cap field and JSON mode they accept; the live certification observes the actual behavior and nothing is assumed. A provider without a hard output cap is not certifiable. Provider-side retention of prompts follows the provider's terms (SYSTEM_SPEC §11 limits); the operator's attestation records what they checked.
11. **Out of scope.** Subscription OAuth harnesses — Claude Code with `CLAUDE_CODE_OAUTH_TOKEN`, Codex exec (Codex inference remains Task 14), the Copilot SDK, Cursor and similar — are separate future routes. Each runs an agent harness with its own tools, settings and state and needs its own harness isolation probe; none is a direct-API dialect.

## Consequences

An operator can choose the Claude CLI, the Anthropic Messages API (including a key funded by a plan's included API credits), any OpenAI-compatible Chat Completions provider, or a local server, by writing one probe configuration and running the same two commands (`probe_provider.py --route-out`, `check_provider_runtime.py`). Everything downstream of the backend — reservation, charging, persisted proposals, admission, health — is unchanged and backend-agnostic. B1 remains open: no live run has happened in this repository, and this session's credentials and proxy are never a route. Health keeps reporting inference unavailable until an operator's live certification writes a certified route.
