# Decision 0012: Consolidation, autonomous revision, FailureRecheck and the dependency index

Status: accepted (Task 10) · Date: 2026-10-18 · Host observed: Claude Code 2.1.301 fixtures (capture); no live route (B1)

## Context

Task 10 builds consolidation and revision (SYSTEM_SPEC §3.5, §6.2–§6.3, §7.2–§7.4; DATA_CONTRACTS §5, §7.1, §8, §10, §11; ACCEPTANCE_TESTS A18–A22, A43, A44, A51, A62) on the Task 5 application path, the Task 8 lineage and the Task 9 admission and review path. The documents fix the rules: deterministic volatile/stable review classes (30/180 days, earlier on dependency change); a changed dependency sets `needs_revalidation` and suppresses caution at once; FailureRecheck in the ingestion transaction before any model call, by certified order, never asserting the historical failure false; conditional historical truth retained; no automatic contradiction from a success; supersession reviewed for inferred and declaration-based replacements; unresolved user-intent conflicts surfaced as one question without blocking; derived writes never re-triggering themselves; existing job types only. They leave open what records a pending revalidation and what may clear it, what "certified order" is for a host whose payloads carry no time or sequence (Claude 2.1.301 hooks), where dependency fingerprints come from when the model cannot compute them, what a queued `revalidate` job decides and with which operations, how an explicit replacement of active guidance stays atomic when the replacement still needs its review, what a candidate does with a counter-observation, how consolidation picks groups and avoids loops, and how the `revalidate@1` prompt fits decision 0009's versioned prompt code. Task 10 needed one answer for each. Nothing here weakens a rule; where a rule was ambiguous the stricter reading was taken.

## Decisions

1. **Rechecks are records (schema 6).** Every reason a claim needs revalidation is one `claim_rechecks` row, keyed by claim, reason and the observation that caused it (`rchk_` + SHA-256), so a replayed or repeated cause records nothing twice: `later_success` and `order_unknown` (FailureRecheck), `dependency_changed` (also transitively, through claim dependencies), `source_conflict`, `review_due` and `consolidation`. The first four set `needs_revalidation` on live guidance: a new claim revision with `review_due_at` now, the counter-observation as a `context` link, a content-free audit operation (kind `recheck`, causal root = the observation) and an advanced guidance epoch, in the caller's transaction (`revalidate.mark`). A due review and a consolidation group leave freshness alone (lack of use is not evidence). The row is `pending` until settled (item 6), `deferred` for a candidate (item 7), `cleared` with an outcome code.
2. **`ClaimRevision.context`** (contract addition; Task 5 stored these links only as normalized rows): counter-observations are carried on every later revision, validated as `context` links, never support (lineage reads only `supports`) and never `contradicts`. **`ReviseClaimPayload.retry_conditions`** (contract addition, failure lessons only, `retry_conditions_require_failure_lesson` otherwise): "retain with an explicit retry condition" is a reviewed revision. Schemas regenerated.
3. **FailureRecheck** (`revalidate.failure_recheck`, called from `capture.pipeline.ingest_ready` for every newly inserted event, before any model call, whatever the budget). A certified success (`tool_finished`, tool channel, `observed_tool`, not derived, result received, outcome success) with a **known** action family (`capture.normalize.action_family_digest`; an unknown working directory or an inexact parse is null and matches nothing) is compared with every live failure lesson indexed by that family on `claim_heads.action_family_digest`, in a compatible workspace scope, that does not already cite it. **Certified order** (`revalidate.certified_order`) is, in this order: the adapter's source sequence within one host session and origin stream; the adapter-reported occurrence time of both events; the capture time of two live, synchronous host hooks of one certified adapter under tool authority. Never commit order or processing time. Claude 2.1.301 hook events carry no sequence and no occurrence time (decision 0005), so the third rule applies to them: the fast path stamps `recorded_at` inside the synchronous host callback, before acknowledgment; a transcript-recovered or imported event never qualifies. Later than the lesson's latest supporting failure (`FailureBody.last_supporting_failure_event_id`, code-derived, decision 0011) → `later_success`; earlier (a late-delivered segment, an old replay) → nothing; equal or not comparable, or no supporting failure reference → `order_unknown`, which suspends caution but asserts no later success. A duplicate event is not inserted, so a replay never rechecks. Nothing is labeled `contradicts`, invalidated or changed in status; the historical failure stays true as history.
4. **The dependency index.** `dependencies` rows of current claim revisions, by kind and key (schema 6 adds an index on claim dependencies). Changes come from the ingestion transaction: a certified exact-parse result with `action_kind` `write` or `delete` names its paths (recorded in `artifact_writes`; the new value is unknown, since the host does not report bytes), and a new current environment observation names its key with fingerprint `SHA-256(["environment", key, value])`. A change whose new fingerprint equals the recorded one preserves applicability (a dependency-preserving change or merge does nothing); any other change marks the claim and then every live claim depending on it (`claim` dependencies, bounded to 16 levels and 256 claims, cycle-safe). `revalidate_dependents(ctx, changes)` (DATA_CONTRACTS §11) applies the same to explicit `DependencyChange`s and enqueues their revalidation. **Fingerprints are resolved by code** at admission (`revalidate.resolve_dependencies`): `file` — the current workspace bytes, but null (unknown) when a certified write to the path was observed after the claim's latest event evidence; `environment` — the one current observed value; `config` — null (no registered parser); `claim` — the dependency's content fingerprint (content key and whether it is still guidance; bookkeeping revisions keep it). A proposed non-null fingerprint must equal the resolved one (`dependency_fingerprint_mismatch`); a missing claim dependency is `dependency_claim_missing`. Limit: a file changed outside any captured tool between the evidence and admission is attributed to the admission-time bytes; the live check at delivery still compares current bytes.
5. **The advice gate** (`revalidate.guidance`, consumed by Task 11): scope and conditions (`conditions.applicability`) decide eligibility; for a failure lesson the dependency gate (`conditions.dependency_applicability` over current file bytes, the query's environment and claim content) decides only *caution*: a changed, missing or unknown dependency caps the lesson at context with a freshness warning (SYSTEM_SPEC §7.3) instead of hiding it. Caution needs active status, supported or corroborated strength, `true` applicability, a `true` dependency gate and `current` freshness; disputed guidance is `conflict`; a candidate is labeled context.
6. **What a revalidation job does.** It is an existing `revalidate` job (protected pool) naming its claims and the observations of their pending rechecks; the request consults those observations first and names them in its read set (they are trimmed last). The model returns existing kinds only: nothing for a claim (keep), `revise_claim` (narrow, revise, add retry conditions: a reviewed candidate revision), `change_claim_status` (`disputed`, `superseded` with an existing active replacement, `invalidated`, `archived`) or `attach_evidence`. It applies through `apply_proposal` like any other proposal; afterwards (`revalidate.settle`, same transaction) each pending recheck of its claims is settled **only when the read set holds the recheck's observation and the still-current claim revision** (otherwise the proposal was requeued, item 9, or the recheck stays pending, `counter_observation_unread`). A revision, a status change or a newer confirming failure settles it (`revised`, the status, `reconfirmed`); a keep settles everything except a `later_success` on a failure lesson (`retain_requires_retry_condition`: narrow, add a retry condition, retire or dispute) and an unresolved source conflict (`source_conflict_unresolved`; only a new authoritative observation resolves one, so no model job is queued for it). When nothing that suppresses caution remains, the claim is `current` again, its strength is recomputed and its next review is a full period away. A job with no recheck a model can settle (a root-class merge, item 10; retired targets) is cancelled `revalidation_settled` without a call, by the planner or the preparer.
7. **Deferred rechecks.** A candidate is not guidance, and a new revision would make its persisted review batch stale. A FailureRecheck or dependency change for a candidate is recorded `deferred` (no revision, no job); the transaction that activates it through a supported review folds them in (freshness, context links), turns them `pending` and queues the revalidation. So a fix observed while a lesson waits for review still caps its caution from the first moment it is guidance.
8. **Gates on active guidance** (admission). An invalidation must cite a `contradicts` link (`invalidation_requires_contradiction`): a success is context, not refutation. The worker can neither invalidate nor archive an active user-declared decision or preference (`declaration_requires_user_intent`), and supersedes one only with an active user-declared claim of the same kind; disputing it (which surfaces the conflict) stays possible. The guarded operator transport (Task 12a) keeps its immediate correction.
9. **Explicit replacement is atomic, after review.** Decision 0011 refused superseding active guidance with an unreviewed candidate. Now a worker supersession of an active or disputed claim naming a candidate replacement (a local ref or an existing candidate) is admitted `review_required` (`replacement_pending_review`) and held in `pending_supersessions`; the target stays active. The transaction in which the replacement's own supported review activates it also supersedes the target (both revisions, `supersedes`/`superseded_by`, the relation) when the target is still at the held revision; otherwise the hold is `stale` and both get a revalidation. A rejected or retired replacement withdraws its hold; a retired target makes other holds stale. A stale revalidation result coalesces into the claims' current revalidation instead of a parallel job.
10. **Root-class merges** (decision 0010 item 6): the merge now recomputes the affected guidance's strength in its ingestion transaction (a merged count can lower `corroborated` to `supported`); its queued revalidation needs no model and is settled. A merge never sets `needs_revalidation`: it changes counts, not applicability.
11. **Review classes** (`revalidate.review_class`, A51): volatile for a failure lesson, any file/config/environment dependency, any volatile, missing or cyclic transitive claim dependency (the claim itself counts as already visited) and every case not listed as stable; stable only for a user-declared decision or preference with no dependencies (the strict reading of SYSTEM_SPEC §6.3: a declaration depending even on stable claims is "another case"). Due 30/180 days after the revision; a freshness recheck makes review due now.
12. **The planner** (`controller/planner.py`, deterministic lane, every poll, no budget, existing job types only, one short transaction opened only when a read finds work): settles revalidation jobs that need no model; schedules due reviews (`review_due` rechecks, no freshness change, skipped while any recheck is owed); opens intent questions; runs routine consolidation when 20 settled episodes accumulated or 24 hours passed (from the last run, initially from installation creation) with new evidence; withdraws holds whose replacement retired. **Candidate groups** are exact proposition-key groups of live guidance whose members overlap (scope dimensions intersect, conditions not certainly disjoint: different `environment_equals`, `branch_ref`, `action_kind` or `tool` values, or non-overlapping version ranges are disjoint) and are not related by supersession; conflicts (different propositions) come first, user-intent conflicts before others, cosmetic duplicates last; at most four groups get a job per run, in band 6 (`jobs.BAND_CONSOLIDATION`). Same-key claims under disjoint conditions are not a conflict (A18).
13. **Causal loops.** Rechecks start only from new events (a success, a write, an environment observation, a source conflict) or the planner's clock; claim writes start none. A consolidation group's recheck key is the content of its members (proposition, scope, conditions, cited support), not their revision numbers, so the revalidation's own bookkeeping revisions never re-trigger it; a due review is skipped while a recheck is owed; assessments still never schedule reviews (decision 0011). Every derived revision keeps its causal root: the triggering observation for a recheck, the job for a settled revalidation, the requeue chain's root for applied proposals.
14. **Intent questions** (A44, `intent_questions`): two or more live user-declared decisions or preferences in one candidate group with different propositions are one open question (`qst_` + SHA-256 of the sorted claim IDs, created once), resolved when fewer than two remain live. Nothing is resolved for the user (no supersession, no dispute by code) and nothing blocks; the group also gets one consolidation job, and creating or resolving a question advances the guidance epoch. Serving it once per session in the next relevant packet is Tasks 11/12b.
15. **Prompts.** `prompts/revalidate_v1.md` is package data and *is* version `revalidate@1` (followed by the shared curator rules), replacing the Task 7 inline placeholder, which no model ever received (no route was ever certified, B1) and which no readable store can pin: schema 6 refuses every older development store. Its digest is pinned by `test_revalidate_prompt_is_versioned_package_data`.
16. **Schema 6.** Migration `0006.sql` adds `claim_rechecks`, `pending_supersessions`, `intent_questions`, `artifact_writes`, `planner_state` and indexes on claim dependencies and due reviews; `SCHEMA_VERSION` becomes 6. A schema-5 development store is refused, never migrated silently (decisions 0007–0011; Task 17). The new tables hold identities, digests and reason codes, no content.
17. **Failpoints.** `recheck.after_mark`, `revalidate.after_settle` and `planner.after_schedule` form the `failpoints.REVISION` family, armed only programmatically. ID prefixes `rchk` and `qst` are registered (hook wire tables regenerated).

## Consequences

Wired now: FailureRecheck, dependency changes and source conflicts in the ingestion transaction; deferred rechecks; revalidation settling; the advice gate; dependency fingerprint resolution; review classes; held supersessions; merge strength; the planner (settling, due reviews, consolidation groups, intent questions). Consumer-side hooks for later tasks: Task 11 composes `revalidate.guidance` into packets (and its live hook-side dependency check for at most 16 files), renders open `intent_questions` as one `conflict` item and labels candidates and `needs_revalidation` guidance; Task 12a's guarded `correct`/`declare` transports produce operator events whose replacement candidates use this review and supersession path unchanged; Task 12b deduplicates questions per session and fences delivery against the guidance epoch these changes advance; Tasks 15/16 make the new tables participate in retention and forgetting; a resolver for `config` fingerprints and for detecting file changes made outside captured tools (a branch checkout, an editor) is later work. No live revalidation quality is claimed: every model behavior in the tests is a recorded proposal, and ACCEPTANCE_TESTS §5 revision gates stay unavailable until B1 clears.
