# Decision 0024: The revision hash chain and the integrity scanner

Status: accepted (Task 5 full slice, Cut 2) · Date: 2026-10-22 · Observed: deterministic tests on real captured events, applications, forget, backup and restore; no live route needed (B1 still open)

## Context

SYSTEM_SPEC §10 defines a full-profile content-digest revision chain: each committed mutation records its sequence, the previous entry's hash, its operation ID, the affected record/revision digests, the tombstone epoch and a canonical metadata hash in the same transaction. Default `doctor` checks the entries since its persisted last verified head and the rows they touched; `doctor --full-integrity` checks the whole chain and every current row digest. Preview reserves the `revision_chain` table (migration 0001) and reports the chain unavailable. A65 full requires incremental range/coverage, full-row detection of an edit to an unchanged row, and an honest baseline when the chain is added to a preview store.

The documents left open: which writes produce an entry, the canonical byte format of an entry and of a row digest, which tables are covered, how a writer's affected rows are found, where the verifier's checkpoint lives, how forgetting and restore interact with the history, and what health and `doctor` report in each profile. This record settles them. Nothing here relaxes a preview rule.

## Decisions

1. **Profile gating.** Only a store whose `installation_meta.release_profile` is `full` records or verifies a chain. A preview store never arms the capture, never writes `revision_chain`, and every integrity form reports `unavailable_in_preview` (`verify` raises `capability_unavailable`; `doctor` reports `checks.revision_chain: "unavailable_in_preview"`; `doctor --full-integrity` exits 4; health keeps `revision_chain` `unavailable` with `deferred_full_release`, `revision_chain_unavailable_in_preview`). `init --release-profile full` stays refused (exit 4) until the full release is otherwise complete: this slice builds the chain, it does not make the full profile available. The tests create full-profile stores through the same provisioning function with a full `ProjectConfig`; there is no production switch.

2. **One entry per write transaction.** In a full store every write transaction that changes at least one chained row appends exactly one entry, inside that transaction, after its rows and the store-revision update and immediately before `COMMIT`. This covers `Store.transaction` (every service, worker, retention, forget and backup write, and restore's staging transaction on its in-memory copy) and the two raw-connection writers, store creation (`db.create_database`) and the operator rebind (`identity.rebind_installation`). A transaction that changes nothing chained (an idle poll) appends nothing; reads never append. Because the entry commits with the rows, a kill anywhere leaves either both or neither.

3. **Capture.** `integrity.arm(conn)` installs, once per connection, a TEMP table and TEMP `AFTER INSERT/UPDATE/DELETE` triggers on every chained table that note each touched row's table, rowid and primary-key JSON. `PRAGMA recursive_triggers = ON` makes the implicit deletions of `INSERT OR REPLACE` visible. TEMP objects live only on the connection: they never reach the database file, a WAL, a backup or a restore copy, and a rollback or a savepoint rollback discards what they captured, so an aborted atomic group leaves nothing in the entry. Writers do not register rows themselves, so none can forget to. `integrity.seal(conn, purge=…)` digests each touched row as it stands at commit (absent rows as `null`) and appends the entry. No model or network call runs in it; hooks never write SQLite and are unchanged.

4. **Chained tables.** Every ordinary table of the main schema (`PRAGMA table_list`, type `table`) except `revision_chain` itself and SQLite's internal tables. Projections (`context_views`, `lookup_candidates`, `lookup_postings`, `retrieval_docs`, `lexical_index`, `projection_state`) are included because the hook serves their bodies; the FTS5 `lexical_fts` virtual table and its shadow tables are not ordinary tables and are excluded (a derived ranking index, rebuilt on restore). A table's identity key is its declared primary key; the two keyless tables (`dependencies`, `lexical_index`) are keyed by rowid.

5. **Canonical format** (DATA_CONTRACTS §11). Canonical JSON is `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)` in UTF-8.
   - Typed value: `["n"]`, `["i", int]`, `["r", float.hex()]`, `["t", str]`, `["b", hex]`.
   - Row digest: SHA-256 of `[table, [[column, typed value], …]]` in declared column order.
   - Key digest: SHA-256 of `["key", table, key]`, where `key` is the primary-key values as SQLite's `json_array` renders them (`[rowid]` for keyless tables).
   - `row_digests` column: canonical JSON `{entry_schema: 1, kind: baseline|mutation|purge, store_revision, metadata_hash, operation_ids, rows}`; a baseline adds `reason: init|activation` and `tables` (the chained tables then). `rows` is `[[table, key_digest, rowid, row_digest|null], …]` sorted by table and key digest, one item per touched row (its last state). `metadata_hash` is the row digest of the `installation_meta` row at commit. `operation_ids` lists the `operations` rows the transaction wrote, in write order.
   - Columns: `sequence` (1, 2, … contiguous), `previous_hash` (the previous entry's hash; 64 zeros before the first), `operation_id` (the first of `operation_ids`, else null), `purge_marker` (1 exactly for `kind: purge`), `tombstone_epoch` (after the transaction), `entry_hash` = SHA-256 of canonical `[sequence, previous_hash, operation_id, row_digests, purge_marker, tombstone_epoch]`.
   - The reserved column set of migration 0001 is unchanged: no schema migration, `SCHEMA_VERSION` stays 11, preview stores and backups are unaffected.

6. **Content-free entries, forgetting and purges.** An entry holds table names, SHA-256 digests, rowids, operation IDs and counters only, never prose or a raw key (a key can carry a path or source key, so only its digest is stored). Authorized purges mark their transaction (`Txn.purged()`): forgetting's purge (also when restore applies newer tombstones), retention's payload expiry, derived-body aging, bookkeeping aging and the forgetting override's payload release. Their entries are `kind: purge` with the removed rows recorded as `null`. Forgetting never rewrites or deletes earlier entries: the history keeps the digests of rows that are now gone. Like a tombstone's source digests, a digest can confirm a guessed value but never yields content; forgotten text appears nowhere in the chain (A65 test, `forget_scenarios.marker_locations` over every table).

7. **Baselines.** A fresh full store's first entry is a baseline (`reason: init`) over every row it holds after creation. Activating the chain on an existing preview store (the full upgrade's activation step, SYSTEM_SPEC §10.1, not built here) calls `integrity.establish_baseline(txn, reason="activation")` in the activation transaction, after the profile is `full`: one baseline over the current rows at the current store revision. It never invents entries for earlier mutations; verification reports `pre_baseline_history: not_chained` for an activation baseline (`none` for an init baseline). A second baseline on a chained store is refused (`policy_refused`); a preview store's call is `capability_unavailable`.

8. **Verification** (`integrity.verify(ctx, full=…)`), in one read snapshot of a read-only connection.
   - Linkage, over the checked range: contiguous sequences (`sequence_gap`), each `previous_hash` equal to the previous stored hash (`chain_link_broken`), recomputed hash (`entry_hash_mismatch`), well-formed body consistent with its columns (`entry_malformed`), non-decreasing store revision (`store_revision_regressed`), a baseline first (`missing_baseline`), and the last entry's store revision equal to the store's (`head_store_revision_mismatch`).
   - **Incremental** (default `doctor`): the range is the entries after the trusted checkpoint (the whole chain when it is missing or untrusted). The last recorded state of each row those entries touched is compared with the store through its rowid (`row_digest_mismatch`, `unlogged_deletion`, `unlogged_row` for a row recorded removed that exists). It cannot see an out-of-band edit to a row no entry in the range touched; the report says so with `coverage: rows_touched_in_range`.
   - **Full** (`doctor --full-integrity`): the whole chain from its baseline, replayed into each key's last recorded state, then every current row of every chained table by key digest: a row the chain does not hold is `unlogged_row`, a recorded row that is gone `unlogged_deletion`, a differing digest `row_digest_mismatch`. O(store) time and memory; the report carries `cost` (`entries`, `rows_scanned`, `tables`, `seconds`) and the CLI prints table-by-table progress on stderr.
   - Findings are content-free (`code` with `sequence`, `table`, `key_digest`), at most 256 listed with `finding_count`. The report also gives `head`, `baseline`, `pre_baseline_history`, `checkpoint`, `checked_range`, `entries_checked`, `rows_checked`, `purge_entries`, `coverage`, `complete_coverage` and `full_integrity_required`.

9. **The verifier's checkpoint** is the private file `.recalith/state/integrity.json` (created 0600, atomic replace): `{checkpoint_schema: 1, installation_id, sequence, entry_hash, store_revision, complete, mode, verified_at, last_result}`. It is never in the store, so `doctor` keeps the store read-only and a backup or restore never carries it. A clean check advances it to the head; `complete` is true only for a clean full check or a clean incremental check from a complete checkpoint. A check with findings never advances it and records its codes as `last_result`. A checkpoint whose sequence is missing or whose hash differs from the chain's (a restore of an older backup, a rewritten chain, an edited file) is `untrusted`; until a clean full check, coverage is not complete (`full_integrity_required: true`). `complete_coverage` therefore means: every entry from the baseline to the head has been verified, the rows each range touched compared when it was checked, and the store's every row compared at the last full check.

10. **doctor, CLI and health.**
    - `doctor` in a full store verifies first (incremental, or full with `--full-integrity`) and reports the verification object as `checks.revision_chain`. A report with findings adds `revision_chain_findings` to `degraded`, so it exits 8 even when every required capability is healthy. A store this engine cannot serve reports `store_not_servable` (and `--full-integrity` exits 4).
    - Health (read-only, no verification) reports `revision_chain` in a full store from the chain head, its baseline and the checkpoint file: `unavailable` (`revision_chain_missing_baseline`), `degraded` (`revision_chain_findings` from the last check, `revision_chain_not_verified`, `revision_chain_checkpoint_untrusted`, `revision_chain_full_check_required`) or `healthy`, with `head_sequence`, `baseline`, `checkpoint`, `entries_since_checkpoint` and `last_result` in its coverage. It never gates readiness. A healthy chain with unverified entries adds the coverage gap `revision_chain_unverified_entries:N`.

11. **Failure injection.** New failpoint family `failpoints.CHAIN`: `chain.before_seal` (rows written, entry pending) and `chain.after_seal` (entry appended, commit pending). The full-profile kill/restart matrix (`test_full_profile_chain_crash_matches_reference`, `CHAIN` + `WORKER`, real worker-written claim/task/episode revisions) requires the restarted store to equal the full-profile reference and the chain to be contiguous, to end at the store revision and to verify over every current row. Like every failpoint it is armed only by a test in its own process.

## Limits (stated, not hidden)

- **Same-user rewrite.** A process of the same OS user that rewrites rows, chain entries and the checkpoint consistently is not detected. This is detection of out-of-band edits by processes that do not also recompute the chain, not an independently trusted log.
- **Incremental coverage.** An edit to a row no entry since the checkpoint touched is found only by the next full check.
- **Rowid locators.** Incremental row checks locate rows by rowid. An operator `VACUUM` may renumber the rowids of keyed tables and make the next incremental check report mismatches; the full check identifies rows by key digest and is unaffected. The engine never vacuums.
- **Cost.** Full-profile writes pay the trigger capture and one digest per touched row at commit; the full check holds one map entry per key ever recorded. Preview writes pay nothing: the profile test reads the metadata row the transaction already reads.
- **Not built here:** `init --release-profile full`, the upgrade's activation transaction (Task 17 full), chain heads in backup manifests, and installed private-path rules (A65's other full part, Task 13 full).

## Consequences

- A65's full variant has its chain and row verification parts implemented and tested; the variant stays `in_progress` because the installed private-path rules (Task 13 full) remain, and nothing is passed while a live variant remains.
- DATA_CONTRACTS §11 (the `revision_chain` row and the entry format) and §12 (`doctor` checks), SYSTEM_SPEC §10 (which writes produce entries, the checkpoint location), and IMPLEMENTATION_PLAN Task 5 (files) are updated; ACCEPTANCE_TESTS needs no change (A65 already states the measurement), and `tests/coverage_manifest.json` names the tests.
